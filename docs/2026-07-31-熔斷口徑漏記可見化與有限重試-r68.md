## 一句話

真錢部位在交易所已經平掉、但「已實現損益」查不到時，舊碼會印一行中文然後**把那筆紀錄永久刪掉**——
而那筆金額正是日 60U／週 150U 熔斷的**唯一輸入**。少記一筆，熔斷就算少一筆，
風險上限被悄悄放寬，而且沒有任何人會知道。

v170 把它改成：**先重試、真的拿不到才承認漏記、並且漏記本身要進帳本擋住你。**

## 一、這是同一種病的第六次

專案裡反覆出現的缺陷物種是：

> **「要用來下判斷的量，只以 log 文字或代理值存在＝等於不存在。」**

前五次：
- v164 —— 健康檔**讀**失敗被吞 ⇒ 對外呈現成「沒有故障史」
- v166 —— 健康檔**寫**失敗只有 log ⇒ 後續全部判斷建立在沒寫進去的東西上
- v167 —— 用「旗標」當「模擬盤活著」的代理 ⇒ 帳本謊報 active 達 51 小時
- v169 —— 意圖過期丟棄只有 log ⇒ 斷流吃掉的訊號數量無人可查
- （r64 同輪）demo 停擺原因只在 log ⇒ 帳本看不到

**第六次（本輪）與前五次的差別，也是它更嚴重的地方**：前五次全都落在**觀測性**——
看不到，但錢沒事。這一次直接落在**風險限制器本身**：漏記的是熔斷的分母，
它會讓「今天已經虧多少」被低估，於是熔斷該關的時候不關。

## 二、原本的碼哪裡破

`manage_positions()` 對帳分支（原 851-857 行附近）：

```python
            print(f"🏁 {rec['inst_id']} {rec['pos_side']} 已了結，"
                  f"已實現≈{pnl:+.2f} USDT（記入 {dk} UTC，該日累計 …）")
        else:
            print(f"🏁 {rec['inst_id']} {rec['pos_side']} 已了結（損益查詢失敗，"
                  "不計入熔斷口徑）")
        ps["open"].pop(iid, None)          # ← 不論成功失敗都刪
```

`_realized_pnl_since()` 有三條會回 `None` 的路：
1. OKX 回 `code != 0` —— 這條有經 `_okx` 記錄；
2. exit code 0 但吐出**非 JSON** —— **完全靜默**，甚至還把 `_ROUND_OKS["ok"]` 加了一；
3. JSON 解析丟例外 —— **完全靜默**。

而 `pop` 是無條件的。合起來就是：
**可重試的事被做成不可逆**——沒有重試、沒有計數、沒有健康欄位、沒有帳本欄位、沒有告警。
下一輪本地帳裡已經沒有這筆，永遠不會再去查。

## 三、v170 做了什麼

### 1. 先重試，別急著刪（`PNL_RETRY_MAX = 5`）
查不到就把 `pnl_retry` 計數寫回**部位檔**，`continue`，下輪再查。
連 5 輪都拿不到才承認漏記並移出本地帳。

> ⛔ **用「輪數」不用牆鐘**：真錢執行器是 Windows 排程每分鐘拉起的**全新行程**，
> 記憶體內的計數活不過一輪。計數必須落在 `_save_positions(ps)` 寫出去的部位檔裡。

### 2. 漏記變成一個有名字的故障類別 `pnl_unaccounted`
- 進 `_CLASS_PRIORITY` 的**最前面**——它是唯一**不可逆**的類別。
- 但它只可能在「帳戶部位查詢成功」的那一輪被記上，所以它不會把一場斷流的真正病因（例如 401）洗掉。
- 新增 `_CLASS_HINT` 說明：告訴使用者這筆錢要自己去 OKX 對，並指名去看 `pnl_unaccounted_recent`。

### 3. 健康檔新增三個欄位
`pnl_unaccounted_total`、`pnl_unaccounted_last_ts`、`pnl_unaccounted_recent`（上限 20 筆）。

三個**刻意**的設計選擇：
- **不拆「故障期／健康期」**（不像 `_account_expiry` 那樣拆）——漏記不論在哪種期間發生，
  對熔斷的傷害一模一樣，拆開只會給人「這個比較不嚴重」的錯覺。
- **不記金額**——金額正是我們查不到的那個量。寫 0 就變成謊報，那就回到紅線③。
- **在 idle-round 提前返回之前就記帳**（v169 學到的同一課：空轉輪的早退會把新統計整段吃掉）。

### 4. 進監督帳本的 blockers
`ceo_oversight.pnl_gap_verdict()`，掛進 `assess()` 的 **blockers**（球在使用者）——
只有人能去 OKX 把金額查回來，也只有人能決定要不要在一個低估的熔斷底下繼續跑。

> ⛔ **與 `live_exec_verdict` 的刻意差異：不套新鮮度閘。**
> `consecutive_fail_rounds` 是「現況量」，健康檔太舊代表執行器沒在跑，拿舊 streak 當今天的阻塞是舊快照陷阱，所以它該被擋。
> 但 `pnl_unaccounted_total` 是**累計的既成事實**：漏掉的損益不會因為執行器停了就補回來。
> 對它套新鮮度閘 ＝ 執行器一停、真實且不可逆的漏記就從帳本上消失，
> 那正是 v162–v167 一路在修的「把已知壓回未知」。這裡改成標注「截至 …」時間，但**永不整條消失**。

## 五、⛔ 給後來者的勿回改清單

- ⛔ 不要把 `pnl_gap_verdict` 加上新鮮度閘（理由見三-4）。
- ⛔ 不要在漏記紀錄裡填一個金額（哪怕是 0）。
- ⛔ 不要把重試計數改成記憶體變數或牆鐘時間——每輪都是新行程。
- ⛔ 不要把 `pnl_unaccounted` 從 `_CLASS_PRIORITY` 首位往後挪。
- ⛔ `pnl_unaccounted_total > 0` 是 **BLOCKED_ON_USER**，不是可以自己清掉的噪音。
