# Phase 0 的「真實 N/30」計數器，讀的那張表沒有任何寫入者

- 日期：2026-08-03（監督員 r126）
- 性質：**決策項**，不逕行修。理由見文末「為何不逕行」。
- 相關：v231（同一物種的另一半，已落地 16e9f07）

## 一句話

CEO 自評每天印的「真實 0/30」，那個 0 **不是量測出來的**——它讀的資料表自 7/08 起就沒有
任何程式在寫，而真錢執行器從頭到尾不曾寫進去。已經了結的 3 筆真錢交易，結構上永遠不會
被算進這個數字。

## 實測證據（本輪逐項量測，非推論）

1. `l3_dispatcher/ceo_session.py::phase0_status()` 的 `live_n = _count_closed("trades")`，
   條件是 `status='closed'`。
2. `trade_journal.db` 的 `trades` 表：共 **101 列，status 全部是 `expired`，`closed` 零列**，
   最後一次寫入約 2026-07-08。
3. 真錢執行器 `tools/atk_consumer/consume_intents_live.py`：全檔**沒有任何**
   `trade_journal` / `record_entry` / `record_exit` 呼叫。它只寫 `atk_positions_live.json`
   （open + day_pnl）與 `atk_live.log`。
4. `trades` 表的唯一寫入端是 `l3_dispatcher/dispatcher.py` 的訊號流（寫進場、逾時改 expired）。
5. 對照事實：真錢已了結 3 筆，全部有帳可查——
   7/29 QQQ +0.94U、8/02 SNDK-USDT-SWAP long +7.03U、8/02 ORCL-USDT-SWAP long +1.59U
   （來源：daemon 自己的 `atk_live.log` 與 `atk_positions_live.json`）。
   ⛔ 這是帳本已實現數字，**不是績效宣稱**；3 筆無統計意義（紅線③）。

## 為什麼這是問題

Phase 0 解鎖進度那一行寫「真實 0/30」，讀者（本人）合理會讀成「真錢還沒開始跑」。
但真錢管線已經開過單、也已經了結過。0 的真正意思是「這個計數器的來源沒人寫」，
兩者差很多：前者是「等樣本」，後者是「這個閘不論再等多久都不會動」。

這與 v231 是同一物種的兩半：
- v231 治的是「**沒有 t 值**時不得斷言 edge 沒問題」。
- 這一個是「**計數器來源沒有寫入端**時不得把 0 印成量測結果」。

## 為何不逕行修（交由本人拍板）

Phase 0 解鎖的門檻是三閘之一：**真實 30 筆「人手實單」+ 律師確認 + 本人拍板**。
「機器人自動下的真錢單算不算數」正是門檻本身的定義問題——改「什麼算數」等於動解鎖門檻，
屬紅線③邊界，必須由本人決定，AI 不得自行認定。

⛔ 尤其：**絕不可為了讓數字動起來而放寬閘**。

## 三個選項（待本人擇一）

- **A. 維持只算人手實單**：那就得補一條「人手實單如何入帳」的路徑（目前完全沒有），
  否則這個 0 永遠不會動。
- **B. 機器人下的真錢單也算**：則需把真錢執行器的了結寫進 `trades`（含 `net_r` 淨值口徑，
  否則 v149 的淨值閘會擋著，`live_gate_reason` 會變成 `live_net_missing`）。
- **C. 兩軌並列**：計數器維持 A，但另外顯示「真錢已了結 N 筆（機器人下單）」，
  兩個數字都不會被誤讀。

## 本輪可安全逕行、但未做的最小修補

不論本人選 A/B/C，都可以先做一件不動門檻的事：讓 `live_gate_reason` 能明說
「此計數器來源目前無寫入端」，而不是只回 `live_sample_short`（＝樣本不足，暗示只是還沒累積）。
