# 告警層自己的健康檔：「讀失敗」不等於「沒有故障史」（r55 · v164）

日期：2026-07-31（監督員 Layer 2 第 55 輪）
影響檔案：`tools/atk_consumer/consume_intents.py`（模板）→ `consume_intents_live.py`（真錢副本，已同步）

## 一句話

真錢執行器的**告警層**把「健康檔讀不到／讀壞了」當成「這台機器從來沒故障過」，
於是連續故障計數每輪從零重數、永遠到不了告警門檻——**告警層自己會無聲死掉**，
而它的唯一職責就是「不讓失敗無聲」。這是 v143（連續 fail-closed 告警）要治的同一個物種，
只是這次的病人是治療者本人。

## 病灶（改動前的碼）

```python
def _load_health() -> dict:
    try:
        return json.loads(HEALTH.read_text(encoding="utf-8"))
    except Exception:
        return {}          # ← 任何讀失敗都變成「乾淨的空白歷史」
```

`finish_round()` 每輪都 `update_health(_load_health(), ...)`。健康檔一旦壞掉：

1. `consecutive_fail_rounds` 回到 0 → 這輪重數成 1；
2. `should_alert()` 要求連續 ≥ `FAIL_ALERT_AFTER`(3) 輪才告警 → **永遠到不了**（若壞檔反覆發生）；
3. `first_fail_ts` 一起消失 → 就算後來告警了，「已持續 N 分鐘」也會被低報；
4. `last_alert_ts` 消失 → 恢復通知的前提（曾告警過）也被抹掉。

壞檔不是理論風險：舊 `_save_health()` 是「先截斷再寫」的**非原子寫**，
行程被砍（排程逾時／休眠／當機）就會留下半截 JSON——本機已有 utf16 壞碼前例，
`_save_positions` 也正是因為同一原因在 r54 被改成原子寫。
而且 `_save_health()` 的例外是 `pass` 掉的：寫不進去，一個字都不會有人知道。

與 r53（孤兒擋單閘的「未知」分支）、r54（本地部位帳讀失敗被當成空帳）同一族：
**把「我不知道」寫成「沒有」**。

## 修法（v164）

1. `_load_health()` 回 `dict | None`：
   - 檔案不存在（且無備份）＝首跑，是真的沒有故障史 → `{}`（合法）；
   - 主檔壞掉 → 退回 `.bak`（last-known-good）**續算**，持續時長不被低報；
   - 兩份都壞 → `None`＝**未知**。
2. `_save_health()` 改「暫存檔 + `os.replace`」原子寫，並另外原子寫一份 `.bak`
   （兩次分開的寫，行程被砍時最多壞掉其中一個）；回傳 bool，失敗會印出來。
3. `finish_round()` 遇到未知時，方向取 fail-closed：
   - 把基準設在門檻前一輪（`FAIL_ALERT_AFTER - 1`），這輪只要有故障就**立刻告警一次**；
   - 同時把 `health_state_unreadable` 記進本輪故障類別（讓這件事本身有出口）；
   - 告警後健康檔會被重寫成好的＝**自癒**，下一輪起恢復正常冷卻，不會變成每分鐘洗版。
4. `health_state_unreadable` 在 `_CLASS_PRIORITY` 排**最後**：它是告警層自己的內傷，
   永遠不該蓋掉同一輪真正的交易故障當代表（否則使用者看到的主因會被換掉）。

### 刻意不做的事

- 沒有把「未知」當成「有故障」去累加計數（那會虛報連續輪數）——只借用門檻前一輪當基準。
- 沒有在寫入失敗時發 Telegram：磁碟滿／權限壞會變成每分鐘一則，告警疲勞比一時安靜更糟。

## 殘留缺口（誠實紀錄，留給後續輪次）

`_save_health()` 寫不進去時，計數會**凍結在舊值**（不是歸零，方向仍保守），
但這件事目前只進日誌、不會主動出聲。屬同族的下一個治本點。
