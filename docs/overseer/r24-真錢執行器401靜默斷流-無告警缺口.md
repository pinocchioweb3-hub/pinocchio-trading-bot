## 一、事實（實查 `atk_live.log`，非推測）

今晚美股開盤（21:30 台北）之後，實盤消費器每分鐘嘗試送單，交易所端一律回 **HTTP 401：
呼叫端 IP 不在該 API key 的白名單內**。到 22:34 為止：

| 項目 | 實測值 |
|---|---|
| 401 次數 | **61**（`atk_live.log` 275 行中，自第 32 行起全是這個家族） |
| 被擋標的 | **SNDK**、**SOXL**（今晚兩檔美股訊號，皆做多、各 3 腿） |

| 今日真錢盈虧 | **0** |

**fail-closed 正確運作**：設槓桿呼叫失敗後，每一腿都印
「本輪不下這腿（fail-closed，下輪重試）」而**不送單**。
所以不是「下了一半」，是**一張都沒下**——沒有半殘的倉、沒有錢受損。
這是 v139–v142 那批風控設計第一次在真錢路徑上被真實事件檢驗，而它**擋住了**。

## 二、時間界線（誠實標註不確定處）

## 三、根因性質：不是設定錯誤，是會復發的結構問題

住宅浮動 IP 被 ISP 重新指派 → 交易所端白名單失效。
今晨成交、今晚被擋，中間沒有任何人改過設定，這個形狀本身就是證據。
**下次重撥還會再發生一次。**

## 四、真正的缺口：**沒有任何告警**（交棒工程席）

連續 61 次認證失敗，沒有 Telegram、沒有進 ledger、沒有任何主動通知。
要不是這輪巡邏翻了日誌，它會安靜地躺著——而躺著的每一分鐘都是**真錢驗證期的空轉**。

**這是同一物種的第三次**：
1. 07-09 demo `halt` 殘閂靜默鎖 intake **19 天**（v137 已補自動復核）
2. 07-12 組織週報排程無聲斷檔 **16.4 天**（`lastRunAt` 只記觸發不記成功）
3. 今天：真錢執行器認證斷流，**零告警**

共同病理：**失敗被寫進某個沒有人讀的地方**。前兩次都靠監督員肉眼撞見才被發現，這次也是。
所以治本方向不只是補這一個告警，是**任何 fail-closed 的連續發生都必須有出口**。

**建議修法（監督員未自行施作，理由在下）**
- 改的檔是 `tools/atk_consumer/consume_intents.py`（**不是** `consume_intents_live.py`——
  實盤副本由 `make_live_copy.ps1` 從它產生，直接改副本會在下次重跑時被蓋掉）。
- 內容：同一標的連續 N 輪 fail-closed（建議 N=3）→ 推一次告警，並設抑制窗避免每分鐘洗版。
  認證類錯誤（401）應與一般查單失敗分流，因為前者**永遠不會自己好**。
- 驗收：收工前當場製造一次假失敗，確認告警真的出得來（勿只看程式碼推論）。

**未自行施作的理由**：該檔同時是模擬盤消費器本體、且是真錢路徑的產生器，
改壞會讓執行器無聲停擺（不會亂下單，但會中斷驗證期）。屬須走防踩踏流程的常駐模組，
依監督員守則「不確定就不動，改記任務交由人工」。
