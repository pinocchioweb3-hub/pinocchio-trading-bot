**日期**：2026-07-31 05:10（台北）
**CEO 狀態**：BLOCKED_ON_USER（真錢側 401 IP 白名單，唯一解在本人；健康帳顯示連續 53 輪 fail-closed，
零下單、零損失）。程式軌本身很活躍——四小時內 v144→v151 共八個版本落地。
**本輪動作**：不硬推被卡的決策；挑等待期可並行、且**不需動 daemon、不需 RB-1** 的一項做完。

## 一、發現（上一輪點出、本輪親讀原始碼證實）

`tools/atk_consumer/verify_live.ps1`（真錢執行器的人工驗收腳本）有兩個缺陷，且兩者互相加乘：

**缺陷一｜第 3 段開頭 `Remove-Item $log` 會刪掉 `atk_live.log`。**
那支 log 是真錢側**唯一**的鑑識紀錄（現約 390KB）。人最想跑驗收腳本的時機，正是「覺得執行器怪怪的」
那一刻——也就是證據最珍貴的那一刻。這個設計等於：**一懷疑就先把證物燒掉，再開始調查。**
7/30 的 401 靜默斷流之所以能事後追出「全檔 739 次 401 只有一個 IP 從沒變過」，靠的就是這支 log
沒被刪過；同樣的事故若有人先跑一次驗收，就再也追不出來了。

**缺陷二｜第 26–27 行把「log 空」判成 `CLEAN (empty log = healthy idle round)`。**
這正是同日 v151 才治掉的那道假等式：**沒有故障訊息 ≠ 已痊癒**。
`run_live_once.ps1` 只在有輸出時才寫檔，所以「log 空」有三種完全不同的成因：
(a) 真的成功呼叫且無話可說、(b) **空轉輪**（沒有合格 intent，執行器根本沒碰過交易所）、
(c) 腳本壓根沒跑起來。舊版把三者一律印成 healthy——7/31 的假恢復（r32 誤判「已恢復」）
就是同一物種：**拿「安靜」當「健康」**。v151 已在 daemon 側治本，但這支人工腳本仍留著舊口徑，
等於留了一個會對人說謊的第二出口。

## 二、修法（v152，本輪落地）

1. **不刪檔，改用位元組位移隔離本輪輸出**：執行前記下 `atk_live.log` 的長度，執行後只讀新增的尾段
   （檔案被輪替/截斷時自動退回讀全檔）。隔離效果與刪檔相同，鑑識紀錄零損失。
2. **定性一律改吃健康帳差分**，不再看 log 空不空。讀 `atk_consumer_live_health.json`
   執行前後的差，對照 v151 的欄位分成四類，且**只有一類算健康**：
   - `rounds_seen` 沒動 → ❌ 本輪根本沒跑起來（不是健康）
   - `last_ok_ts` 前進 → ✅ **成功呼叫輪**——唯一能證明真錢執行器活著的證據（若同時有
     `recovered_from` 則附註本輪也是恢復輪）
   - `idle_rounds` 前進 → ⚠️ **空轉輪**，明寫「這不構成健康證明」並附上連續故障輪數
   - `consecutive_fail_rounds` > 0 → 🚨 故障輪，附 class 與連續輪數，並註明 fail-closed 未下單
3. 第 3 段開頭加一行明示警語：**本段會真的跑一次真錢執行器**，若當下有合格 intent 就會送出真實訂單。
   舊版把這件事藏在 `== 3) clean round ==` 這種無害字樣底下。

## 三、為什麼這次沒有程式碼 commit（重要，別當成漏做）

`verify_live.ps1` 在 **v148（72af242）已被刻意列入 `.gitignore`**，與真錢執行器其餘本機側檔案一起，
目的是讓「誤 git add 真錢側」在機制上不可能發生。本輪尊重該防護，**未使用 `git add -f`**，
修好的檔案只存在本機。因此本文件即是它的公開可稽核紀錄：上面第二節寫得夠細，
足以在檔案遺失時原樣重建。

## 四、驗證方式（未執行真錢路徑）

本輪**沒有**執行該腳本的第 3 段（那會呼叫真錢執行器）。改用不執行的靜態驗證：
- `[Parser]::ParseFile(...)` → PARSE OK，零語法錯誤。
- 從 AST 取出中文字串常數比對碼位（⚠=9888、空=31354）→ 確認 PS 5.1 解碼正確
  （檔案已補 UTF-8 BOM；無 BOM 時 PS 5.1 會以 Big5 讀中文而爆掉，同 `start_bot.ps1` 舊傷）。

真正的功能驗證要等 401 解除後、下一次有人手動跑驗收時自然發生；屆時應看到
「✅ 成功呼叫輪」而非舊版的 `CLEAN`。
