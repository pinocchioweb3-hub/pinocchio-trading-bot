## 1. 一句話結論

盤點帳本 `system_faults` 長期掛著的「產品總監／CoinGlass 稽核官**排程仍未自產＝未驗收**」，

這兩席之所以還沒「自產」，唯一原因是**它們自修補之後一次都還沒輪到開火**——
不是修了還壞，也不是原因不明。

- 產品總監下一次開火：**2026-08-03（一）09:39 台北**（本文寫成時約 6.4 小時後）。
- CoinGlass 稽核官下一次開火：**2026-08-04（二）09:30 台北**。

⛔ 這個區別很重要：帳本那句話讀起來像「有個沒人知道原因的故障還在」，
實情是「原因已知、修補已部署、只是還沒到第一次驗收機會」。把後者長期顯示成前者，
本身就是本專案打了 49 次的同一個物種——**把「未知／未到期」講成「壞掉」**，方向相反但同樣不誠實。

## 2. 根因（2026-07-29 已診斷）

排程層的 `lastRunAt` **只記「觸發」不記「成功」**。一席被觸發、跑到一半預算用盡、
什麼檔都沒留下，排程層仍然記一筆漂亮的 `lastRunAt`⇒ 對外看起來「有跑」，實際零產出。
研判主因：各席提示都把**多項讀取工作排在寫檔之前**，session 預算先被讀取吃光。

**修法**（2026-07-29 起陸續落到各席 `SKILL.md`）：

- **開場第一件事**就先建立 `docs\org\digests\<role>-YYYY-MM-DD.md`，寫入標題、日期、「產製中」與各節空標題。
- 之後**每完成一節就立刻回寫**，不留到最後一次寫完。
- 預算不足以完成全部時，在檔尾誠實註明「本期未完成的節：X、Y」——**留下不完整的週報，遠優於什麼都沒有**。

## 4. 為什麼帳本分不出來（且本輪不主張改碼）

`ceo_oversight.py` 的組織產出檢查是**檔齡制**：掃 `docs/org/digests/` 各席最新自產檔的日期。
它手上只有「檔在不在」，沒有「排程有沒有開過火」「提示是什麼時候改的」——
結構上就分不出這三種狀態：

1. 開火了、失敗了（真故障）
2. 開火了、成功了（健康）
3. **還沒輪到開火**（未到期，本案）

要讓它分得出來，得去讀 Claude 排程器自己的 `lastRunAt` 儲存區。
⛔ **本輪不做**：那會讓交易 daemon 去耦合一個外部工具的內部狀態檔，
路徑與格式都不在本專案掌控內，是拿一個脆弱依賴換一行顯示文字，划不來。
正確做法是**由監督員在交棒裡承擔這個區分**（本文即是），而不是硬塞進 daemon。

⚠️ 另note：帳本的 `org_coverage` 視圖其實**已經**正確標了 `pending_period`
（產品總監「2026-07-27→2026-08-03 尚未到期·僅代補產填過」），沒有把未到期的那期算成缺報；
會誤導的是**檔齡制那句 `system_faults` 文字**。兩個視圖的口徑一致，只是文字讀起來不一致。
