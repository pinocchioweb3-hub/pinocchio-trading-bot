## 三、本輪做的事（v143）

改 `tools/atk_consumer/consume_intents.py`（**範本**，不是 live 副本——
live 副本由 `make_live_copy.ps1` 產生，直接改會被下次產生蓋掉）：

1. **失敗分流成可行動的類別**。`classify_failure()` 把 CLI 失敗分成
   `auth_ip_whitelist`（要人去後台補白名單，會復發）／`auth`（金鑰簽章權限）／
   `cli_missing`（要重裝）／`rate_limit`（會自癒）／`timeout`／`query_fail`（下游症狀）／`other`。
   混在一起就只剩「有錯」這種沒人會動作的資訊。
   **「查無此單」（51603）明確判為良性**——那是冪等查詢的正常答案，
   誤記成故障會讓告警天天誤鳴，誤鳴的告警等於沒有告警。
2. **單一掛鉤攔全路徑**。失敗登記做在 `_okx()` 裡，槓桿／查單／下單／對帳／損益查詢
   全部自動涵蓋；回傳值與交易邏輯**完全沒動**，只多一個副作用。
   另在 `place()` 真正「該下卻沒下」那一刻補記 `query_fail`——那才是零成交的瞬間。
3. **健康檔＋連續計數**（`atk_consumer_health.json`，live 為 `atk_consumer_live_health.json`）：
   連續故障輪數、首次／最近故障時間、各類別次數、最近錯誤原文（key id 已遮蔽）、
   告警管道與管道自身的錯誤。這是給人和機器讀的持久出口，不是 log。
4. **告警**：連續 **3 輪**（＝3 分鐘）有故障才發（單輪抖動不吵），同類故障每 60 分鐘再提醒一次
   （故障還在就不准轉安靜），**換了故障類別立刻再報**（新故障不被舊冷卻蓋掉）。
   走 Telegram，`urllib` 標準庫、維持本腳本零依賴；憑證先讀環境變數再讀 `.env`
   （排程器環境沒有那兩個變數，這是實測確認的），**永不列印憑證值**。
5. **恢復也有出口**：故障消失時發「已恢復」通知並重置冷卻。無聲恢復同樣會讓人誤判。
6. **告警管道自己失敗也留痕**（`last_alert_channel` / `last_alert_error`）——
   否則就變成「告警的無聲失敗」，同一個坑再踩一次。
7. **告警層永不拋例外進交易路徑**（`finish_round()` 整段包住）。
   監控壞掉可以接受，監控把執行器弄掛不可接受。
8. **告警文字守紅線③**：只講連線狀態，明確寫「這是『沒下單』不是『虧損』」，
   不夾帶任何勝率／報酬／年化字樣（有測試把這四個詞列為禁字）。

配套：`make_live_copy.ps1` 加 `-GenerateOnly` 開關（只重產 live 副本，
**不動排程、不跑任何一輪**），並補上健康檔的 live 檔名替換。

### 為什麼這次不必走 daemon 防踩踏（RB-1）
`tools/atk_consumer/` 不在 daemon 常駐模組裡，是 Windows 工作排程器每分鐘
以 `--once` 驅動的獨立進程。改檔不影響正在執行的那一輪（Python 已載入記憶體），
下一輪自然吃到新碼。最壞情況是寫檔瞬間被讀到半個檔→解析失敗→該輪不下單（fail-closed）→下輪正常。
