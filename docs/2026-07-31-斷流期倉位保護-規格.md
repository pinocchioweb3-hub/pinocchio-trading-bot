# 斷流期倉位保護——規格（r46・監督員 Layer 2）

> 狀態：**規格＋離線測試已落地；偵測函式已就位但尚未接入主迴圈。**
> 接入會改動交易語義（多一條可能擋單／可能送出平倉的路徑），依規矩不在無人值守的
> 排程輪次做。本文把「該做什麼、為什麼、怎麼驗收」寫死，讓下一輪（或有人值守時）
> 可以照著接，不必重新推導。
> 對應程式：`tools/atk_consumer/consume_intents.py` 的 `orphan_positions()`；
> 測試：`tests/test_atk_consumer.py` 的 r46 區塊（7 支）。

---

## 一、這件事的由來

2026-07-30 起真錢執行器因 OKX API 金鑰 IP 白名單不含目前出口 IP，連續數百輪
HTTP 401、每輪 fail-closed（未下單、零損失）。事後量測（r37）留下一條沒答完的問題：

> **④ 斷流期間如果手上有真錢倉位怎麼辦？**
> 401 會同時鎖死「進場」與「出場」。這次帳上 `open={}`（無在場倉），
> 所以什麼事都沒發生——但那是**運氣，不是設計**。

本輪把這條問題查到底。結論比原本的擔心**好一半、也壞一半**。

---

## 二、好的那一半：止損不靠我們這一側活著

進場的每一腿都是「市價進場＋附掛 TP＋附掛 SL」的單一 OCO 原語
（`_leg_args()`：`--tpTriggerPx` / `--slTriggerPx`），止損**掛在交易所上**。

⇒ 客戶端斷流（401、斷網、機器關機、排程被刪）期間，在場倉位的止損照樣由 OKX
執行，單筆最大虧損仍是 ≈1R。**斷流不會讓在場倉「裸奔」。**

這條是整個保護設計的底線，已用測試釘住：
`test_partial_leg_failure_sends_a_real_leg_but_reports_failure` 會檢查送出的參數裡
確實有 `--slTriggerPx`。⛔ 任何改動若讓進場腿失去附掛止損，這支測試必須紅。

## 三、壞的那一半：帳本這一側會掉東西

斷流期間掉的不是止損，是**本地帳**，而本地帳餵著三件事：

| 掉的東西 | 後果 | 嚴重度 |
|---|---|---|
| 逾時強平（`timed_out()`，客戶端計時） | 該平的倉會超時續留，直到 TP/SL 才了結 | 中（虧損仍受 SL 上限保護） |
| 了結對帳（`manage_positions()` 記 `day_pnl`） | 斷流期間了結的損益延後入帳 | 低（v154 修B 已改成吃「成交日」而非「對帳日」） |
| **日／週熔斷口徑**（吃 `day_pnl`） | 少算的那筆虧損不會推動熔斷 | **高** |

熔斷是「跨筆止血」的那道閘。少算一筆，等於閘的刻度被偷偷放寬。

### 3.1 真正的破口：孤兒部位

比「延後入帳」更嚴重的是**永久脫帳**。成因鏈（兩端都已用測試釘住）：

1. `place()` 分批進場是多腿；任一腿查單失敗（斷流時必然）就整筆回 `False`。
2. `main()` **只在 `True` 時**才把部位寫進本地帳。
3. 若此時前面的腿**已經成交**——交易所已有倉、附掛 SL/TP 都在——本地帳是空的。
4. 斷流讓後續每一輪都在同一步失敗，直到該 intent 過了 `expires_at`（6h）被丟棄。
5. 從此：交易所有一個真錢部位，本地帳完全不知道它存在。

而 `manage_positions()` **只從本地帳出發**逐倉去問交易所，從不反過來枚舉交易所側
（本地帳空時它連問都不問就返回——`test_manage_positions_is_structurally_blind_to_orphans`）。
⇒ 孤兒部位在結構上永遠看不見：不會逾時平倉、了結損益永遠不進 `day_pnl`、
`dup_open_same_side()` 也看不到它（同幣同向可能再開一筆＝曝險翻倍）。

> 📌 本次斷流沒有踩到，是因為斷流開始時手上沒有倉、且斷流期間每一輪都在
> **第一次查單**就失敗（一腿都沒送出去）。要踩到只需要換一個時序：
> 「先成交一腿 → 才開始斷流」。

## 四、規格：反向對帳（reverse reconciliation）

### 4.1 偵測（已完成，純函式、零副作用）

```python
orphan_positions(exchange_positions, open_map) -> [(inst_id, pos_side, contracts), ...]
```
「交易所上真的有、但本地帳沒有」的部位。`pos=0` 不算（已平）；同幣反向算不同部位
（hedge 合法）；畸形資料一律略過而不丟例外（將來要跑在交易路徑上）。

### 4.2 接入（待有人值守時做）

在 `manage_positions()` 開頭：

1. **無條件**呼叫一次 `account positions`（不可再因本地帳空就提早返回——那正是盲點本身）。
2. 查詢失敗 → 本輪什麼都不做（維持現行 fail-closed，不猜）。
3. `orphan_positions()` 有結果時：
   - **記健康帳**：新增故障類別 `orphan_position`，讓連續輪告警機制自然接手。
   - **發告警**：文字須含 instId／posSide／張數，並明說「此倉不在自動管理之下、
     其止損仍掛在交易所」。⛔ 不得出現任何績效宣稱。
   - **⛔ 不自動平倉**：孤兒的成因是「我們不確定它是什麼」，不確定時動真錢部位
     是把不確定變成損失。平不平由人決定。
   - **⛔ 不自動收編進本地帳**：收編＝自動接管它的逾時強平與熔斷記帳，
     但我們沒有它的 `placed_at`／進場價／R 值，收編會製造假帳。
4. **擋單**：偵測到孤兒時，同幣同向的新 intent 本輪不接（比照 v154 修A 的
   `dup_open_same_side`，理由完全相同：hedge 併倉會讓已實現損益無法歸屬）。
   這是唯一該自動做的「動作」，而且方向是保守側。

### 4.3 驗收條件

- 新增測試須**先在接入前的碼上失敗**（本專案硬規：非虛設檢定）。
- `test_manage_positions_is_structurally_blind_to_orphans` 的預期要同步改成
  「有枚舉交易所並回報孤兒」——那支現在是特徵化盲點，接入後它就該翻面。
- 迴圈級測試（非只純函式）：孤兒在場 → 同幣同向新單被擋、反向不被擋。
- 查詢失敗輪：不得把「查不到」當成「沒有孤兒」（fail-closed 方向）。
- 改完模板後必跑 `make_live_copy.ps1 -GenerateOnly`，並讓
  `tests/test_live_copy_parity.py` 綠（v157 的逐字比對會擋下「忘了重新產生副本」）。

## 五、不做什麼（刻意）

- **不把止損改成客戶端管理。** 現在止損掛在交易所是這套設計最強的一點，
  客戶端補一層只會在斷流時比交易所更早失效。
- **不在斷流期間試圖「保護性平倉」。** 斷流的定義就是送不出去；能送出去就不是斷流。
- **不因為孤兒而放寬任何既有閘。** 三道閘（is_active／kill_switch／demo_guard）
  與 fail-closed 語義 ⛔ 永不弱化。
