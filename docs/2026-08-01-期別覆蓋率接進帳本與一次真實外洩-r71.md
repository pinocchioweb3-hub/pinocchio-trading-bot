影響面：監督帳本 `l3_dispatcher/ceo_oversight.py`、清理器 `tools/atk_consumer/redact_log_backfill.py`

## 一句話

第一件是計畫中的：帳本原本只看「各席最新報告有多舊」，任何一份新檔都會把它前面的
歷史缺口一起蓋掉——現在帳本每輪都會寫出「近 N 期到底交了幾期」。

第二件是撞上的：跑全套測試時，repo 自己的洩漏閘紅了——**上一輪（r70）那支
「秘密清理器」，自己的測試素材裡寫了使用者真實的出口 IP，並且已經隨 e7c3b3b
推上 PUBLIC repo**；而那一輪的紀錄寫的是「secret_leak_scan 乾淨」。

## 一、期別覆蓋率（v173）

### 舊的盲點

`org_digest_verdict()` 是**檔齡制**：只看該席最新一份自產 digest 有多舊。
它答得了「這席現在是不是停擺中」，答不了「過去 N 期交了幾期」。

真實例子（2026-07-31 人工逐檔清點才發現）：

| 創意總監 | 7/08 | 7/15 | 7/22 | 7/29 |
|---|---|---|---|---|
| 自產 | ✅ | ❌ | ❌ | ✅ |

檔齡制看到「最新是 7/29、才兩天前」→ 判無斷檔。那兩期缺報**從未上過任何一輪帳本**。

### 修法

`org_digest_coverage.py`（r52 就寫好、零 import 進 daemon 的純模組）本來只能手動跑，
本輪把它接進帳本：新增純函式 `org_coverage_verdict()`，`build_snapshot()` 每輪呼叫，
結果寫進帳本新欄位 `org_coverage`。

### ⛔ 刻意不做的事：它不改 CEO 狀態

覆蓋率講的是**既成事實**（過去 N 期交了幾期），現況停不停擺仍由檔齡制負責。

如果把已經結束的歷史缺口也丟進 `system_faults`，該席明明早就恢復了，CEO 狀態仍會被
壓成 STALLED 長達整個回看窗（12 期）＝慢性假警報，最後連真的那一則也一起被忽略。
這正是 r66 memguard 那件事的教訓（例行噪音一天 101 則，會埋掉唯一在等的訊號）。

所以這一欄只負責**讓事實每輪出現在帳本上**，判斷留給人。日後若要升級成告警，
需要的是「長期低度交付」的判準（例如近 12 期只交 4 期），那是另一次刻意的決定。

### 一個踩得到的技術點

`org_digest_coverage` 反過來 import `ceo_oversight`，所以 `ceo_oversight` 這邊的
import **一定要留在函式內**——搬到檔頭就是循環匯入，daemon 直接起不來。程式碼裡已註明。

### 驗收

- 新測試 14 則，**先在改動前的碼上跑過**：兩條「不可弄壞的既有行為」護欄綠
  （檔齡制對已結束的缺口仍回 None；檔齡制的斷檔仍進 system_faults 並壓成 STALLED），
  新行為紅（`assess() got an unexpected keyword argument 'org_coverage'`）＝非虛設檢定。
- 改動後 14 綠；`ceo_oversight` 自測 62/62；`org_digest_coverage` 自測 14/14；全套 1266 passed。
- RB-1：停 watchdog → 停 daemon → 改 → py_compile → 測 → 單次乾淨重啟
  （單一新 PID 11996、`bot.err.log` 不存在、liveness 新鮮）→ watchdog 已復原。

## 二、本輪撞到的真實外洩（r70 的自我更正）

### 事實

跑全套測試時 `tests/test_secret_leak_scan.py` 兩則紅，命中：

```
tools/atk_consumer/redact_log_backfill.py:211  key_id
tools/atk_consumer/redact_log_backfill.py:213  public_ip
tools/atk_consumer/redact_log_backfill.py:218  public_ip
```

那是 r70 寫的清理器，它的自我測試素材直接抄了真實日誌原文——包含**使用者家用網路的
真實出口 IP**。該檔隨 commit `e7c3b3b`（7/31 23:42）推上 origin/main，而 repo 是 PUBLIC。

**r70 那一輪的紀錄寫的是「secret_leak_scan 乾淨」。** 這句話當時就是錯的——閘是好的、
測試也早就存在（v161 就寫了），只是那一輪沒有真的跑到它。這是今晚同一物種的第八次：
**拿代理值當事實**。前七次傷的是觀測性與風險上限，這一次傷的是公開面。

### 已做的處置

測試素材換成掃描器自己認得的假貨（判準就寫在 `tools/secret_leak_scan.py`）：

- key-id 佔位 → `00000000` 開頭的 UUID
- IP 佔位 → RFC 5737 文件用網段 `203.0.113.0/24`

清理器自測 19/19 仍全綠（含「IP 不被遮」那條回歸鎖——IP 不遮的口徑沒有被動到，
改的只是測試素材），全套 1266 passed，`tools/secret_leak_scan.py` 全域掃描回報乾淨
（範圍：追蹤中檔案 + 最近 50 筆 commit 訊息）。

### ⚠️ 誠實話：修掉檔案 ≠ 把它從網路上收回

`e7c3b3b` 已經公開過。改掉現在的檔案只讓**往後**的 clone 看不到它，**git 歷史裡那一版
仍然存在**，任何人 checkout 舊 commit 都讀得到。要真正抹掉必須改寫已公開的歷史
（force-push），那會動到所有人的 clone，**不是我可以單方面決定的事**——已列入待你決策。

### 這件事的嚴重度（不誇大也不淡化）

- 洩漏的是**出口 IP**，不是金鑰。知道 IP 的人**仍然沒有** API key／secret／passphrase，
  無法用它下單或提領；OKX 的 IP 白名單是「少了它就不能用」，不是「有了它就能用」。
- 但它是家用網路的位址（屬個資範疇），且本專案自己立過「出口 IP 永不進 repo」的規矩。
- 現實上它還會自然失效：這個 IP 是浮動的，換過就與現在的你無關。

## 三、⛔ 給後來者的勿回改清單

1. `org_coverage` **不得**加進 `system_faults`、不得改 `state`——理由見上（慢性假警報）。
2. `ceo_oversight` 內對 `org_digest_coverage` 的 import **不得**搬到檔頭（循環匯入）。
3. `org_coverage_verdict(exclude_roles=...)` **只**影響「哪些是新發現」，**不刪資料**——
   已被檔齡制報過的席次，覆蓋率數字照樣留在 `roles` 裡。
4. `org_coverage` 欄位在無缺報時值為 `None` 但**欄位必須存在**——Layer 2 才分得出
   「沒缺報」與「這版沒這功能」。
5. 測試素材**永遠**用掃描器認得的假貨，不要抄真實日誌原文。清理器裡「IP 不被遮」
   那條回歸鎖是對的、不要動；要動的是素材。
6. 宣稱「secret_leak_scan 乾淨」之前**要真的跑**（`python tools/secret_leak_scan.py`
   或全套 pytest）。這一輪證明了：閘存在、測試存在，然後被跳過，照樣外洩。
