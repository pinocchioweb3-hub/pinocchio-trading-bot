# 401 斷流的「實際成本」量測，與今日 10:12 的 v151 自然實驗

日期：2026-07-31 06:40（台北）
作者：監督員（Overseer, Layer 2）r37
狀態：**無程式碼變更**——本輪只做唯讀量測與假說驗證／推翻

---

## 一、為什麼做這一輪

帳本狀態是 `BLOCKED_ON_USER`，唯一 blocker 是真錢執行器的 OKX 401（IP 白名單）。
球在使用者手上，AI 不可代按。但「等」不等於「什麼都不知道」——
先前每一輪回報的都是**抽象數字**（「連續 N 輪被擋」），使用者無從判斷這件事到底
擋掉了什麼、什麼時候會變成不可逆。本輪把它換成**具體、可查證、有時限**的事實。

## 二、量測結果（全部來自本機檔案，唯讀）

資料來源：`atk_live.log`（4028 行）、`atk_consumer_live_health.json`、
`atk_positions_live.json`、`intent_outbox/`、`atk_consumer_live_state.json`。

### 1) 401 的規模與同質性
- 全檔 **887 次** HTTP 401。
- 出現過的 IP：**只有一個**——`<出口 IPv4，見監督員 log／聊天室，本檔不落地>`（零例外）。
  → 與 r35／v153 的歸因校正一致：這**不是**浮動 IP 的結構問題，
    就是**一個 IP 沒被加進白名單**。補這一個就會通。

### 2) 斷流從哪一刻開始（新事實）
- 日誌第 1–17 行＝ 7/30 QQQ 那筆真錢單的三腿（唯一一筆成交過的真錢單）。
- **第 31 行就是第一個 401。**
  → 也就是說：**自那三腿之後，執行器沒有再成功送出過任何一筆單**，
    至今約 **26.5 小時**。不是「偶爾被擋」，是「成交過一次之後就再也沒通過」。

### 3) `last_ok_ts` 是假恢復的化石，不是健康證據（複驗通過）
- health 檔 `last_ok_ts = 07-31 04:12:03`，看起來像「兩小時前還好好的」。
- 但日誌裡 `✅ 執行器已恢復` **只出現過一次**（第 3202 行），
  而它的**前兩行**（3200、3201）正是 `⏭ SOXL 已過期——跳過`、`⏭ SNDK 已過期——跳過`。
  → 兩個 intent 剛好同時過期 → 那一輪零呼叫 → 舊碼把「沒故障」當「乾淨輪」
    → 送出假恢復通知並寫下 `last_ok_ts`。**04:12:03 就是假恢復那一刻本身。**
- 結論：`last_ok_ts` **只能差分讀**（有沒有往前跳），絕不可當「最後一次成功呼叫」。
  這一條先前是推論，本輪在日誌行號層級拿到了**因果直證**。

### 4) 這次斷流的真實成本（可數的部分）
- **已經永久錯過：2 筆**——SOXL、SNDK（各自撐到 6 小時窗尾、過期即棄）。
- **正在倒數：2 筆**
  | intent | 標的 | 建立 | 過期死線 |
  |---|---|---|---|
  | `8f0962fe92b224d0` | SNDK | 07-31 04:12 | **07-31 10:12** |
  | `d7be100abfbbb1d3` | MU   | 07-31 06:12 | **07-31 12:12** |

  執行器每分鐘重試一次，但只能重試到 `expires_at`；過了就標記跳過、永不補送。
  → 使用者若在 **10:12 前**補上 IP，SNDK 還救得回來；12:12 前補，MU 還救得回來。
    這是本輪唯一「有時限」的資訊。

  ⚠️ 誠實界線：「錯過」＝**執行器連嘗試的機會都沒有**，
  **不等於**「少賺了多少」。這些是模擬盤同源的美股突破 intent，
  沒有成交就沒有結果，任何「損失金額」的說法都是捏造，本文不做此宣稱。

### 5) 沒有無人看管的真錢曝險（安全面確認）
- `atk_positions_live.json` → `open: {}`，`day_pnl` 只有 7/29 的 +0.9388。
- 亦即斷流期間**沒有任何一個開著的真錢倉位**因為 401 而管不到（對帳／逾時平倉打不出去）。
  這是本次斷流最大的運氣：若當時有倉在場，401 會同時鎖死「進場」與「出場」。
  → 記為未來的風險項，不是現在的事故。

## 三、被推翻的一個假說（記下來，免得下輪重查）

**假說**：v151／v152（04:41／05:09 提交）可能沒進到正在跑的行程裡——
若執行器是常駐行程，它啟動於修補之前，舊碼還在跑，那 10:12 會再噴一次假恢復。

**推翻**：執行器**不是常駐行程**。`schtasks \ATKLiveConsumer` 每分鐘叫一次
`run_live_once.ps1` → `python consume_intents_live.py --once` → **每一輪都是全新行程**，
必然載入磁碟上的最新版本。實體檔 `consume_intents_live.py` 內已含 v151 的
`_ROUND_OKS` 三態判定（第 68/133/135/203-204/346-349 行）。
→ **修補自 04:41 起即已生效**，不需要重啟任何東西。
（順帶：這也代表改這支檔案不必走 RB-1 停機流程；但它是真錢路徑，仍不由監督員擅動。）

## 四、今日 10:12 的自然實驗（本輪最有價值的發現）

v151 的驗收先前被登記為「等 401 修好、拿到一次成功呼叫才算驗過」——也就是**卡在使用者身上**。
但那只是 v151 的**正向側**（真的通了才准報恢復）。它還有**負向側**：
**零呼叫的空轉輪不得歸零、不得報恢復。**

而負向側**今天會自己發生，不需要使用者做任何事**：

- **10:12** SNDK 過期 → 若期間沒有新 intent 進來，執行器進入零呼叫的空轉輪。
- **12:12** MU 過期 → 同上，第二次機會。

**驗收判準（誰都可以查，只要看日誌）**
- ✅ **通過**：401 仍在的前提下，出現 `⏸ 本輪零呼叫（空轉…）` 這行，
  且**沒有**出現第二次 `✅ 執行器已恢復`，且 `consecutive_fail_rounds` **不歸零**。
- ❌ **失敗**：又冒出一次 `✅ 執行器已恢復`＝v151 沒治到本，同物種第四次。

這把一個「等使用者」的驗收項，換成了「今天午前就有答案」的驗收項。
下一輪監督員（10:15 之後）的第一件事就是查這個，成本一行 grep。
