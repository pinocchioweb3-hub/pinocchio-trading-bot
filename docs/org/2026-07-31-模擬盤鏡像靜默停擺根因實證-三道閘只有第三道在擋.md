# 模擬盤鏡像靜默停擺——根因由「高度懷疑」升級為「實證」，且它不是 bug

日期：2026-07-31（監督員 Layer 2，r43）
狀態：**根因已實證（三道閘逐一量測）。閘本身行為正確、不可弱化。真正待修的是兩個「觀測性」缺口，
以及一個只有使用者能做的決定。**

---

## 一句話

今晨 CEO 日報查出「模擬盤鏡像已靜默停擺 41.6 小時」，並**高度懷疑**是 `demo_guard`
與 7/29 安裝的實盤金鑰互斥。本輪把那三道閘**逐一實測**：閘①過、閘②過、**閘③擋**——
懷疑升級為**實證**。而閘③擋得**完全正確**（它就是設計來擋這個的）；
真正的缺陷是它**擋得無聲**，以及帳本把「旗標開著」講成「鏡像運行中」。

## 一、三道閘逐一實測（唯讀探針，零 OKX 互動）

`run_demo_operator_cycle()`（`l3_dispatcher/demo_operator.py:712-731`）在碰任何交易所之前
有三道閘，任一不過就 `return`。本輪用同一份 `.env`、同一組模組函式逐一評估：

| 閘 | 判定式 | 實測結果 |
|---|---|---|
| ① `is_active()` | 環境變數 `DEMO_OPERATOR_ACTIVE` 是否為真 | 值為 `'1'` → **True，過** |
| ② `dt.kill_switch_active()` | 人工急停閂 | **False，過** |
| ③ `demo_guard.ensure_demo_env()` | 實盤金鑰須全空＋demo 開關開＋demo 金鑰齊備 | **RAISE DemoGuardError，擋** |

閘③拋出的原文：

> 偵測到實盤交易金鑰已設定：['OKX_TRADE_API_KEY', 'OKX_TRADE_API_SECRET',
> 'OKX_TRADE_API_PASSPHRASE']。模擬盤模式下 OKX_TRADE_* 必須全空，以杜絕對真錢下單。

三個實盤槽位**皆有值**，三個模擬盤槽位也**皆有值**，`OKX_DEMO_TRADING_ENABLED=1`。
（本文件不記錄任何金鑰值或長度——repo 為 PUBLIC。）

也就是說：**其他每一道閘都是開的，只有第三道在擋，而且它擋的理由完全成立。**

## 四、為什麼沒有人發現——兩個觀測性缺口

### 缺口一：`skipped` 這條路徑**永遠不出聲**

`run_demo_operator_loop()`（:761-782）：

```python
res = await run_demo_operator_cycle(tg=tg)
if res.get("error"):                    # ← 只有 error 會印
    print(...)
elif not res.get("skipped"):            # ← skipped 直接靜音
    ...
```

閘③把結果寫成 `out["skipped"] = "demo_guard:..."` 而非 `error`，所以走的是**靜音**那條。
這個靜音是**當初刻意設計**的（docstring：「空轉（兩把鑰匙未開）時安靜不洗版」）——
針對的是「使用者根本沒裝模擬盤金鑰」的常態空轉，合理。
但它**同時也吞掉**了「本來在跑、今天開始被擋」這個完全不同的事件。

值得注意的是，**v137 已經替 `halted` 補過同一道傷**（:772-779，每小時至少出聲一次，
註解寫著「7/09 殘閂靜默 19 天的教訓，停擺不可以是隱形的」）。
同一支檔、同一個迴圈、同一個道理——**`skipped` 沒被一起補**。

而且這與今晨 04:41 的 **v151 是同一個物種**：真錢側把「這輪沒有故障訊息」誤當「已經好了」；
模擬盤側把「這輪安靜」誤當「沒事」。**「沒有壞消息」不是「好消息」，只是「沒有消息」。**

### 缺口二：帳本的 `demo_active` 是旗標，不是實測

`l3_dispatcher/ceo_oversight.py:457-460`：

```python
demo_active = False
...
    demo_active = is_active()        # ← 只讀閘①（環境變數旗標）
```

閘①是三道中**唯一過得了**的那道。於是帳本 41.9 小時來一直寫 `"demo_active": true`，
而真實狀態是「每一輪都在閘③被擋回」。今天早上的 `oversight_ledger.json` 仍然如此。

**這不是小事**：它是「用代理值當事實」的同一個物種——與今晨 CEO 日報自己抓到的
`startup_state.json` 時戳 vs 進程建立時間差 30 分鐘、與 r42 證偽的 `nextRunAt` 當健康探針，
是**同一類錯誤的第三次出現**。

## 五、不可以做的事

**⛔ 不可弱化 `demo_guard`。** 它的三層正向證明（設定層／header 層／執行期簽名層）是
2026-06-15 那次「本機同時存在兩條實盤下單路徑」教訓的產物，直接守著紅線①。
「把 `OKX_TRADE_*` 必須全空這條放寬掉」會讓模擬盤自動下單路徑失去對真錢的隔離——
**任何情況下都不做，包括為了讓 Phase 0 樣本動起來。**

## 六、待使用者決定（只有你能決定，已同步進 `WAITING_ON_USER.md`）

這台機器上，**模擬盤鏡像與真錢執行器要不要共存？**

- **(a) 要共存** → 需要把兩組金鑰放進**不同的環境**（例如真錢執行器由排程工作單獨注入
  `OKX_TRADE_*`，daemon 的 `.env` 只留 `OKX_DEMO_*`）。工程上可行，但這是**動真錢金鑰的
  存放方式**，必須你點頭、也必須你親手改，監督員不代做。
- **(b) 不共存** → 接受模擬盤鏡像在真錢驗證期間停擺（這是**目前的實際狀態**）。
  若選這個，**必須同時修掉缺口二**，否則帳本會繼續謊報「運行中」，我們會再一次「以為在跑」。

**兩個選項都不影響紅線①**，也都不需要弱化任何閘。差別只在 Phase 0 的模擬盤那條腿
是要恢復推進、還是明確地標記為「暫停中」。

## 七、交辦（不需要使用者決定，兩個都不弱化任何閘）

### 修 D：`skipped` 比照 v137 的 `halted` 給它一個聲音

位置：`demo_operator.py:766` 那條 `elif`。規格：

- 維持「常態空轉安靜」的原意——**只有當 `skipped` 的理由是 `demo_guard:` 或 `kill_switch` 時**
  才出聲（`inactive(...)` 是使用者沒開，維持安靜）。
- 節流比照 v137：**每小時至多一次**，沿用 `last_halt_log` 的同款計時器（另立變數，別共用）。
- 這是純新增 log 分支，不改任何判定邏輯，不改閘。

### 修 E：帳本 `demo_active` 改成實測

位置：`ceo_oversight.py:460`。規格：

```python
demo_active = is_active()
demo_blocked = None
if demo_active:
    try:
        demo_guard.ensure_demo_env()
    except demo_guard.DemoGuardError as e:
        demo_active, demo_blocked = False, str(e).split("。")[0]
```

- 額外寫一個 `demo_blocked` 欄位進帳本，讓「為什麼不 active」不必再翻程式碼。
- ⚠️ `ensure_demo_env()` 是**純環境變數檢查、不連網、無副作用**，放進帳本產生器是安全的
  （不要改成呼叫 `confirm_okx_demo()`——那會連 OKX，帳本產生器不該連網）。
- ⛔ 錯誤訊息裡含金鑰**名稱**（非值），寫進帳本可以；但帳本若日後外流請注意這點。

### 驗收

- 兩者都在 daemon 常駐模組內 → **必須走 RB-1 防踩踏流程**（停 daemon → 改 → `py_compile`
  → 跑 `tests/` 相關測試 → 單次乾淨重啟 `start_bot.ps1` → 驗單一新 PID／`setup.err.log` 空／
  liveness 新鮮 → 移除 `watchdog.disabled` 重新武裝）。
- 修 E 的驗收訊號很明確：下一份 `oversight_ledger.json` 的 `demo_active` 應為 **false**、
  且 `demo_blocked` 指出實盤金鑰那句。**若它還是 true，就是沒修好。**
- 修 D 的驗收訊號：daemon 重啟後一小時內，主控台應出現一則 demo_guard 擋單的訊息。
