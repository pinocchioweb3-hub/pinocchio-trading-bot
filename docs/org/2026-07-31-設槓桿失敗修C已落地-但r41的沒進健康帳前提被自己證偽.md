# 設槓桿失敗：修 C 已落地——但 r41 的「完全不進健康帳」前提被探針證偽

日期：2026-07-31（監督員 Layer 2，r45）
前篇：`docs/org/2026-07-31-真錢路徑設槓桿失敗-唯一不擋單也不記帳的呼叫.md`（r41）
改動檔：`tools/atk_consumer/consume_intents.py`（模板）→ `consume_intents_live.py`（`make_live_copy.ps1 -GenerateOnly` 產生）
版本標記：v155

## 一、結論（先講最短的版本）

r41 說設槓桿是真錢路徑上唯一「失敗了既不擋單、也不記帳」的呼叫，並據此開出修 C-1
（＝失敗時補記 `_note_fail`）。**這輪把 C-1 拿去實測，發現它是個 no-op：帳早就記了。**

上一輪（r44）交棒時把 C-1 訂為「三修中唯一無爭議」的下一步，理由是它不動交易語義。
現在看，正因為它不動任何東西——**v151 在 `_okx()` 裡放的那個單一掛鉤，早就把包含設槓桿
在內的每一支呼叫的失敗都記進健康帳了**。如果照著交棒指示悶頭做，這輪會產出一個
「已修」的假績效。

真正還缺的是另外兩件，都已落地：

| | r41 的說法 | 實測 | 這輪做了什麼 |
|---|---|---|---|
| 記不記帳 | 完全不記 | **會記**（`auth_ip_whitelist`）⇒ 前提錯 | 改記成可辨識的 `leverage_fail` |
| 類別分得出嗎 | 未提 | **分不出**是哪一支呼叫死的 | 新增 `leverage_fail` 類別＋處置提示 |
| 擋不擋單 | 不擋 | **確實不擋**（回傳 `None`，呼叫端無從判斷） | 只在風險帶 fail-closed（修 C-2） |

## 二、探針（不是讀碼推論，是跑出來的）

把 `subprocess.run` 換掉，只讓 `swap leverage` 這一支回 401、其餘呼叫全成功——
也就是 r41 說「從未出現過、出現了就沒防護」的那一格，直接在離線環境造出來：

```
A) 只設槓桿失敗一輪 → _ROUND_FAILS = {'auth_ip_whitelist': ...}
   ⇒ 進健康帳了嗎： True
B) update_health → consecutive_fail_rounds = 1｜last_fail_class = auth_ip_whitelist
C) class_counts = {'auth_ip_whitelist': 1}｜能否分辨是設槓桿而非查單： False
D) ensure_leverage 回傳值 = None ⇒ 無回傳值可供 place() 判斷 ⇒ 照樣下單
```

**讀法**：B 那行就足以推翻 r41 的第 2 點推論（「只有設槓桿失敗的那一輪會被判成完全健康」）。
那一輪會被判成故障輪、會累加連續故障、達門檻會告警。**「安靜＝痊癒」這個物種在這條路徑上
早就被 v151 治掉了，r41 是在讀舊模型。**

C 那行才是真的缺口，但它比 r41 講的小得多：不是「沒記」，是「記了但標錯層級」——
記到的是**傳輸層**類別（401），從 `class_counts` 看不出死的是設槓桿還是查單。

D 那行是真正有牙齒的那一項，r41 對這點的描述完全正確。

## 三、改了什麼（v155）

### 修 C-1'（校正後版本）：可辨識的故障類別
`ensure_leverage` 失敗時補記 `leverage_fail`，並排進 `_CLASS_PRIORITY`——
**排在 `query_fail` 之前**（查單失敗是下游症狀，設槓桿失敗是根因），
但排在認證／網路類之後（那些會解釋它為什麼死）。告警提示同步寫進 `_CLASS_HINT`。

副作用檢查：`auth_ip_whitelist` 仍排在 `leverage_fail` 之前 ⇒ 目前 401 斷流期間
`last_fail_class` 不變 ⇒ **不會觸發 `should_alert` 的「換類別立刻再報」而洗頻**。

### 修 C-2：只在風險帶擋單
`ensure_leverage` 改回 `bool`；`place()` 在「設槓桿失敗 **且** 算出的 `lev < LEVERAGE`」
時回 `False`、零腿送出、下輪重試。

`lev == LEVERAGE` 時維持現行「只警告、照下」——本執行器只會設 ≤ 上限的值，
交易所舊值不可能比上限更高，擋了是白擋。

**修 C-3（回讀交易所實際槓桿）仍不做**：多一次 API 呼叫、多一個會失敗的東西，
先讓 C-2 在線上跑過若干輪再決定。

## 四、邊界校正：r41 §五 的「≤3.5% ⇒ 20x」要往下修一格

寫驗收測試時撞到的：止損**剛好 3.5%** 時，`leverage_for_trade` 算出的是 **19 不是 20**。
原因是 `int()` 截斷——`70/3.5` 在浮點下是 `19.999…`。

所以風險帶的實際邊界是 **止損 > 3.4% 就可能進得去**，比 r41 寫的寬一格。
方向本身是保守側（槓桿更低＝保證金押更多），**不改**；但 r41 拿這條界線論證
「美股代幣多半落在 20x 那格、風險主要在加密側」的結論要跟著鬆一點。
