## 一、這次要看的不是程式在跑什麼，是程式**怎麼被產生出來的**

真錢執行器 `consume_intents_live.py` 不是手寫的。它是 `make_live_copy.ps1` 拿模板
`consume_intents.py` 做 **11 處字串代換**產生的：

| 項目 | 模板（模擬） | 真錢副本 |
|---|---|---|
| 每筆風險 1R | 100U | **20U** |
| 風險絕對上限 | 150U | **30U** |
| 單筆名義值上限 | 3000U | **600U** |
| 日虧熔斷 | 300U | **60U** |
| 週虧熔斷 | 750U | **150U** |
| 槓桿上限 | 5x | **20x** |
| profile / demo 閘 | demo / `is True` | live / `is False` |
| 狀態・持倉・健康檔 | 共用檔 | 各自獨立的 `*_live.json` |

前四輪（v152–v155）所有的驗收都做在**模板**上：測試跑模板、py_compile 跑模板。
真錢那一支是「產生出來的東西」，沒有人驗過產生器本身。

## 二、PowerShell `.Replace()` 找不到字串時不報錯

```powershell
$s = $s.Replace('RISK_USD = 100.0', 'RISK_USD = 20.0')   # 找不到 → 原樣返回，不報錯
```

沒有回傳筆數、沒有例外、沒有任何跡象。舊版腳本代換完直接寫檔並印
`1) live copy created OK`。所以只要有人動了模板那幾行的寫法——改個空格、改個
預設值、加個註解——對應代換就會**靜默沒發生**，而印出來的還是 OK。

這是本專案第四次遇到同一物種：**靜默 no-op 被當成成功**
（假痊癒空轉輪 / halt 殘閂 / 排程 lastRunAt 只記觸發 / 本次）。

## 三、兩個壞模板實驗（舊碼 vs 新碼，同一份輸入）

在 scratchpad 造兩份「被改壞的模板」，兩邊各跑一次產生器：

**情境 A**：有人把模板預設風險從 `RISK_USD = 100.0` 調成 `90.0`
**情境 B**：有人把模板槓桿從 `LEVERAGE = 5` 調成 `LEVERAGE = 50`

| | 舊碼（git HEAD） | 新碼（v156） |
|---|---|---|
| 情境 A | 印 `live copy created OK`、exit 0，產出 **`RISK_USD = 90.0`**（真錢每筆風險變成預期的 4.5 倍） | throw、exit 1、**一個字都沒寫出去** |
| 情境 B | 印 `live copy created OK`、exit 0，產出 **`LEVERAGE = 200`** | throw、exit 1、**一個字都沒寫出去** |
| 對照組（模板正常） | OK | OK，且產出與現行部署版**逐位元組相同** |

情境 B 是這次才發現的第二個洞，而且比第一個更難看：`.Replace` 是**子字串**比對，
`LEVERAGE = 5` 命中 `LEVERAGE = 50` 的前半，代換後拼成 `LEVERAGE = 200`。
沒有人會在 code review 時看見這一步——它發生在產生器裡，不在任何一份原始碼裡。

## 四、修法（兩端各守一半，都 fail-closed）

**產生器端**（`tools/atk_consumer/make_live_copy.ps1`）
1. 11 處代換收斂成單一真相表 `$subs`（from / to / label）。
2. 每個錨點必須在模板中**剛好命中 1 次**，否則 `throw` 中止——**中止在寫檔之前**，
   不留半成品。
3. 邊界規則：錨點後面接數字或小數點的不算命中（治情境 B）。
4. 代換完再複驗一次：舊值全數消失、新值全數在場。
5. 成功時印出命中筆數（`11 處代換全部命中並複驗通過`），而不是無條件印 OK。

**測試端**（`tests/test_live_copy_parity.py`，8 支，純本地零網路）
- 直接解析 `$subs` 表，逐一檢查錨點是否仍與模板對得上 → **模板一改壞，pytest 當場紅**，
  不必等到下次有人產生真錢副本才發現。
- 風險級常數（RISK／NOTIONAL／LEVERAGE／STOP_USD／PROFILE）若新增卻沒進代換表 → 紅。
- 狀態／持倉／健康檔必須各自獨立（`intent_outbox` 是**刻意**共用，已在測試裡註明例外）。
- 真錢側每一個風險上限都必須嚴格小於模板值。
- PROFILE 轉 live 與 demo 閘反轉必須成對存在（只翻一半＝副本行為未定義）。
- 兩支負向檢定：把模板改壞後檢查必須抓到（證明前面幾支不是空跑）。

**驗收（先失敗再通過）**：8 支測試先在**改動前的產生器**上跑 → 5 紅（表根本不存在）；
改完 → 8 綠。既有 `tests/test_atk_consumer.py` 33 支同步全綠。

## 五、對現行部署的影響：零

用新產生器重跑 `-GenerateOnly`，產出與事故前備份**逐位元組相同**（含 BOM）。
也就是說目前線上跑的真錢副本參數是對的（risk 20U / notional 600U / 日 60U / 週 150U /
20x），本輪只是把「下一次產生」的安全網補上。`py_compile` 模板與副本皆通過。

## 六、本輪自己踩的坑（必須留紀錄）

跑舊碼對照實驗時，我把 `git show` 出來的舊腳本（原檔已有 BOM）用 `utf-8-sig` 再寫一次，
變成**雙 BOM**。PowerShell 因此沒能解析 `param([switch]$GenerateOnly)`，
`-GenerateOnly` 失效 → 舊腳本一路跑到第 2 步 `schtasks /Create`，
把**真實的** `ATKLiveConsumer` 排程指向 scratchpad 裡不存在的 `run_live_once.ps1`。

- **後果**：真錢執行器排程約 11:11–11:13 之間停擺（Last Result -196608＝找不到檔案），
  漏跑約 1–2 輪。期間全部處於 401 斷流，本來也送不出任何單，故無訂單影響。
- **處置**：立即用原參數 `schtasks /Create /SC MINUTE /MO 1` 指回
  `tools\atk_consumer\run_live_once.ps1`，已驗 Task To Run 正確、Status Ready、
  健康帳 rounds_seen 重新遞增。
- **教訓（已入記憶）**：拿舊版檔案做對照實驗時，**別用會二次加 BOM 的寫法**；
  更根本的是——舊腳本第 2、3 步會動到**真實排程與真實執行器**，
  對照實驗應該只跑「產生」那一段，或先把 schtasks 那兩行從對照副本裡拿掉。
  在真錢路徑旁邊做實驗，實驗本身也要 fail-closed。
