### 對照組（同一次查詢，六個排程）

`nextRunAt` 這個欄位在其他排程上看起來都「正常」（週報席都指向下一個對應星期），
唯獨每日席會露出這個現象——因為只有每日席的「下一班」與「再下一班」只差一天，
**跳過一整班在畫面上才看得出來**。週報席若發生同樣的語意偏移，畫面上會長得完全正常。
所以這不是 CEO 席特有的毛病，而是**這個欄位本身不能拿來判斷「下一班會不會跑」**。

## 二、結論一：`nextRunAt` 不是健康探針（證偽，勿再用）

- ❌ **不可用**：「`nextRunAt` 跳過了某一天 ⇒ 那一班會被跳過」。今日實測直接證偽。
- ⚠️ 已知且維持不變：`lastRunAt` **只記觸發、不記成功**（7/28 艦隊稽核定案）。
- ✅ 今日順帶量到一個**可用**的性質：`lastRunAt` 是**觸發當下**就寫入的，不是跑完才寫。
  證據有兩筆——CEO 席名目 01:07:35、`lastRunAt` 01:08:09（+34 秒，而該席產檔要到約
  09:13 台北才落地）；監督員本席 `lastRunAt=01:03:52Z` 正是**本輪自己還在跑的時候**就已寫入。
  所以 `lastRunAt` 是誠實的**觸發時戳**，只是不代表成功。

## 三、結論二：真正該建的探針是「觸發 → 產出」的轉換

7/28 稽核與 r36 歸因校正已經把問題定位得很準確了：**問題從來不是「沒觸發」，
而是「觸發了沒產出」**（14 次未產出全部落在共同故障日，零例外）。
今天這次量測第一次把這條轉換鏈的**兩端時戳**都拿到了：

```
觸發（lastRunAt，可靠）  →  ……5～8 分鐘（實測，見第五節）……  →  產出（docs/org/digests/<role>-<date>.md 落地）
   01:08:09Z                                                          01:16:02Z
```

有了這個延遲基準，正確的偵測器形狀就很清楚：

> **`lastRunAt` 前進到今天的班次 ＋ 已過 T 分鐘 ＋ 對應日期的自產檔仍不存在 ⇒ 該次觸發失敗。**

這條規則只用兩個**已證實可靠**的輸入（觸發時戳、自產檔是否存在），
不碰任何已被證偽的欄位。

## 四、現行偵測器的盲窗有多寬（量化）

現行程式側消費者（v146/v147，`l3_dispatcher/ceo_oversight.py:176 org_digest_verdict`）的判準是：

```python
ORG_ROLE_CADENCE_DAYS = {"ceo": ("CEO 日報", 1), ...}   # 第 82-88 行
ORG_DIGEST_MISS_PERIODS = 2                             # 第 91 行
if age_days <= cad_days * miss_periods:  continue       # 第 203 行：不算斷檔
```

對 CEO 日報（cadence=1、miss_periods=2）：**自產檔要舊到 3 天才會被判斷檔。**
換句話說，今天這一班若真的失敗了，帳本上**今天與明天都會顯示乾淨**，
要到 8/02 才會亮燈——**盲窗最寬 2 天**。

這個 `miss_periods=2` 的設定**本身是對的**（它是為了不誤報而刻意留的緩衝，
且對週報席等於 14 天寬容度，剛好夠吸收一次補班）。問題不在這個常數，
而在於**除了它以外，沒有任何更快的探針**。第三節那條規則可以把同一件事的
偵測延遲從「最寬 2 天」壓到「約 10 分鐘」，而且不必動 `miss_periods`。
