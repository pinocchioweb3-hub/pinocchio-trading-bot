## 發現一：`commit_age_sec` 不分作者，監督員自己的 commit 也算 CEO 推進

`_git_last_commit_age_sec()`（ceo_oversight.py:345-357）就是 `git log -1 --format=%ct`，
**沒有任何作者或訊息過濾**。監督員每輪結束都會 commit 一份 `docs(overseer):` 報告，
這筆 commit 會把 `commit_age_sec` 歸零，與 CEO 是否真的在動完全無關。

這與 **v147 已經治過的物種一模一樣**。v147 的 docstring 原文：

> `backfilled:` ⋯**只影響措辭，不影響是否觸發**：代補產補的是內容，不是排程；
> 排程有沒有修好，只有該席自產檔落地才算證明。**混用會把缺報蓋成痊癒**。

v147 在「組織席次」那條線上把監督員代補產與該席自產分流了，
但**沒有回頭把同一條原則套到 `commit_age_sec`**——監督員的 `docs(overseer):` commit，
就是 commit 這條線上的「代補產」。

## 發現二（更關鍵）：另一個輸入 `real_output_age_sec` 量的是 daemon，不是 CEO

`assess()` 第 275 行是 **OR**：

```python
recent_commit = commit_age_sec is not None and commit_age_sec < stall_sec
recent_output = real_output_age_sec is not None and real_output_age_sec < stall_sec
...
elif recent_commit or recent_output:
    state = "ADVANCING"
```

`real_output_age_sec` 來自 `paper_journal.most_recent_activity_ms()`（paper_journal.py:819-829），
讀的是 `paper_trades` 表的 `MAX(entry_at), MAX(exit_at)`——**紙上進出場是常駐 daemon 產的，
24 小時自己在跑，跟 CEO Session 死活無關**。該函式自己的 docstring 寫得很誠實：
「有新進場/平倉＝**引擎**真在動」——引擎，不是 CEO。但 `assess()` 把它當 CEO 推進的證據用。

**合起來：ADVANCING／STALLED 這條軸的兩個輸入，一個被監督員自己汙染，一個量的是 daemon。
沒有一個在量 CEO。** 一個 CEO Session 完全死掉、而 daemon 照常紙上交易的情境，
會被判成 ADVANCING，永遠不會 STALLED、永遠不會 push CEO。

## 但是——實測把「偵測線已死」這個說法推翻了一半

先有假說，就要拿數據去打它。以 30 分為取樣間隔重播全歷史 `commit_age_sec`，
分「含監督員 commit（現行口徑）」與「排除監督員 commit（真 CEO 口徑）」兩種算法：

| 區間 | 現行口徑越過 12h 門檻 | 真 CEO 口徑 | 差額 |
|---|---|---|---|
| 監督員上線以來全期（6/22–7/31，1869 取樣點） | 1362（72.9%） | 1373（73.5%） | **僅 11 點（0.6%）** |
| 今日 7/31 00:00 起（17 取樣點） | 0（0%），最大 1.7h | 0（0%），最大 2.3h | 0 |

**結論要誠實：歷史上這個汙染幾乎沒有改變過任何一次判定**（1869 點裡只有 11 點會翻面），
今日 CEO 也是真的在動（排除監督員後最大 commit_age 才 2.3h，離 12h 門檻很遠）。
「STALLED 偵測線已死」這個講法**不成立**，我一開始的假說被自己的量測打掉。

真正成立的、有時效的說法是這條**條件式、前瞻性**的：

- 今日監督員 commit 間隔實測為 33／27／32 分（平均 30 分）。
- 以此節奏，`commit_age_sec` 的**理論上限約 0.55 小時**，門檻是 12 小時
  ⇒ **只要監督員維持這個節奏，commit 停滯這條分支在數學上不可能觸發。**
- 監督員的節奏是今天才變密的（6/22–7/30 是零星幾筆／日，7/31 變成每 30 分一筆）。
  也就是說：這個瑕疵**昨天以前只是雜訊，今天才變成結構性失效**——而它的嚴重度
  完全取決於監督員自己的行為，不是 CEO 的。

## 附帶發現：12h 門檻本來就不是有鑑別力的訊號

全期 72.9% 的取樣點都在 12h 門檻之外——**即使完全排除汙染也一樣是 73.5%**。
CEO 是爆發式工作（整夜衝一批 v-series，白天休息），對這種節奏設 12h 門檻，
結果就是「大部分時間都判停滯」。這代表 `commit_age_sec` 這個輸入長期以來
**根本不是決定 state 的那一個**——真正在扛判定的是 `blockers`（球在使用者）
與 v144／v146＋v147 補上的 fault-specific 消費者（真錢執行器健康、組織產出斷檔）。

換句話說：**通用的「停滯偵測器」是裝飾品，真正管用的是針對已知故障species 的專用消費者。**
這也解釋了為什麼這個瑕疵至今零實害——不是因為它被防住了，是因為從來沒人靠它。

## 為什麼本輪不改碼

1. **P2 潛伏、非流血**：實測零實害，且 state 目前由 `blockers` 主導（BLOCKED_ON_USER），
   commit 分支根本沒被諮詢。
2. **`ceo_oversight.py` 是 daemon 常駐模組**，改它要走完整 RB-1（停 daemon → 改 →
   py_compile → 測試 → 單次乾淨重啟 → 驗 PID/err.log/loops/liveness → 重啟 watchdog）。
   為一個 P2 潛伏項在 10:15 實驗窗前停 daemon，風險報酬不對。
3. 沿用「不確定就不要動 daemon，改記任務交由人工」的既定守則。

## 交辦 CEO Session（P2，10:15 實驗之後，可與其他 daemon 側修補合併一次 RB-1）

**修 A｜`commit_age_sec` 排除監督員自產 commit**（v147 原則的回頭套用）
- `_git_last_commit_age_sec()` 改用 `git log -20 --format=%ct%x01%s`，
  以 `^docs\(overseer\)` 與 `^docs: ?監督員` 兩個 pattern 濾掉監督員自產，取第一筆非監督員的 ts。
- 讀不到／全 20 筆都是監督員 → 退回現行行為（回最新一筆），**fail-safe 不製造假故障**
  （比照 v147「目錄為空＝環境問題，回 None 交人工」的守則）。
- 額外回一個 `commit_age_sec_raw` 進 snapshot 供對照，兩者差很多時本身就是訊號。

**修 B｜`real_output_age_sec` 正名，不再當 CEO 推進證據**
- 這個欄位量的是 daemon 引擎活性，不是 CEO 產出。建議在 snapshot 裡改名／加註
  `source: "daemon_paper_engine"`，並重新檢視第 275 行的 OR：
  「引擎在跑」不應該單獨足以判定「CEO 在推進」。
- ⚠️ 這條會**放寬**觸發條件（更容易 STALLED），改動前要先確認不會製造狼來了——
  建議先只加註與 log 對照欄位，觀察若干輪實際分佈，再決定是否動 OR 邏輯。**別一次改到底。**

**測試三條**
- 最新一筆是 `docs(overseer):` → `commit_age_sec` 應回到再前一筆非監督員 commit 的年齡。
- 最近 20 筆全是監督員 → 退回最新一筆（fail-safe，不回 None、不噴例外）。
- 正文含「監督員」但 subject 不是 docs 前綴的 commit → **不**被誤濾（比照 v147 只掃檔頭不掃正文的教訓）。

**不要做的事**
- 不要順手調 `STALL_SEC`（12h）。上面第三節顯示門檻與 CEO 爆發式節奏不匹配，
  但那是另一個題目，要有自己的量測，不要夾帶在本修裡。

監督員每輪 commit 一份報告，而帳本用「最後一筆 commit 多久前」判 CEO 有沒有在推進——
**監督員在替自己要監督的對象打卡**。實測顯示至今幾乎沒改變過判定（1869 點只有 11 點），
但今日監督員節奏變密到每 30 分一筆之後，這條分支在數學上已不可能觸發。
同時另一個輸入量的是 daemon 不是 CEO。兩者合起來：**這條軸沒有任何一個乾淨的 CEO 訊號**——
至今無害，是因為真正在扛判定的從來是 blockers 與 v144／v146 那些專用消費者，不是它。
