## 一句話

去年 v130 在 **模擬盤鏡像路徑**修好的「同幣同向併倉→已實現損益被雙重記帳」，
**從來沒有被移植到真錢的 ATK 執行器**。真錢那條路今天仍然可以對同一個幣、同一個方向
連下兩張單，而 OKX hedge mode 會把它們併成交易所側的**單一部位**——屆時日虧熔斷的
記帳口徑會失真。

目前零實害（真錢史上只送出過 1 筆單），但這不是因為有防護，是因為量還沒上來。

## 證據鏈（全部可複驗）

### 1. 模擬盤側有閘，且當初是踩過雷才裝的

`l3_dispatcher/demo_operator.py:419-428`（v130）：

```python
open_trades = dj.get_live_demo_trades()               # 桶風險：當下在倉清單
# v130（獵捕workflow·真bug治本）：OKX hedge mode 同幣同向會「併倉」成單一交易所
#   部位→一筆 realizedPnl 無法歸屬兩個 intent（LAB/BTC 已實證同一筆 pnl 被雙重記帳、
#   R 虛增 +1.30）。同幣同向已有在場 demo 單 → 拒收新鏡像，杜絕歸屬歧義。
if any(t.get("symbol") == symbol and t.get("direction") == direction
       and t.get("status") in ("pending", "open") for t in open_trades):
    _record("rejected", "reject:dup_pos_merge_risk", None, ...)
    return {"placed": False, "reason": "dup_pos_merge_risk"}
```

注意括號裡那句：**LAB/BTC 已實證**同一筆 pnl 被雙重記帳、R 虛增 +1.30。
這不是假設性風險，是模擬盤上真的發生過、被抓到、才修的。

### 2. 真錢側沒有這道閘

`tools/atk_consumer/consume_intents_live.py` 全檔對在場部位表 `ps["open"]` 只有四處使用：

| 行號 | 用途 |
|---|---|
| 496 | 對帳前判斷「有沒有倉要管」 |
| 506 | 對帳迴圈 |
| 519 | 了結後移出 |
| 746 | 下單成功後**寫入** |

**沒有任何一處把它當成下單前的閘。** 下單迴圈（717-751）依序檢查：已處理過（done）、
human_gated、已過期、日虧熔斷、張數換算——**唯獨不問「這個幣這個方向我是不是已經有倉了」**。

而且 `ps["open"]` 是以 **intent_id** 為鍵，不是以 (inst_id, pos_side) 為鍵，
所以同幣同向的兩筆在資料結構上本來就能並存。

### 3. 觸發窗有多寬：18 小時

兩個週期參數對不上：

- intent 有效期 **6 小時**（`expires_at`）
- 部位逾時強平 **24 小時**（`TIMEOUT_HOURS = 24.0`）

也就是說一個倉最長活 24h，期間上游會把同一個 setup **重新發 2～3 次**。
今天 outbox 的實測就抓到重發行為：

```
SNDK-USDT-SWAP long  舊 intent 到期 07-31 04:03 → 新 intent 04:12 產出（相隔 9 分鐘）
LINK-USDT-SWAP long  舊 intent 到期 07-30 01:53 → 新 intent 07-31 02:20 產出
```

上游不是「一個幣一輩子一張」，它是**到期就可以再發**。所以：
T 時下單 → T+6h intent 過期 → T+6h 上游重發 → 執行器沒閘、照下 →
**在 T+6h 到 T+24h 這 18 小時窗內，同幣同向第二張會被送出去**。

（今天 outbox 的 12 張 ALIVE intent 彼此 inst_id 皆不重複，所以此刻沒有正在成形的
重複單——這是本輪實查的結果，不是推論。）

### 4. 為什麼至今零實害

真錢史上只成功送出過 1 筆（7/30 QQQ），當天了結，`atk_positions_live.json` 至今
`day_pnl` 只有孤零零一筆 `2026-07-29: +0.94`，`open` 是空的。7/30 之後 401 斷流，
連續 202 輪零送出。**沒被咬到是因為樣本只有 1，不是因為有防護。**

## 一旦踩到，壞在哪

三層，由輕到重：

1. **曝險翻倍且無人察覺**：張數是「每張單各自照 20U 風險」算的，
   併倉後同一個標的實際扛 2R，而每單一次的名目上限（v84）是逐單檢查的，攔不到總和。
2. **已實現損益雙重記帳**：`_realized_pnl_since(inst_id, since)` 只用 instId 篩，
   不分 posSide、不分 intent。兩張單在同一輪一起被判定「已了結」時，
   各自從自己的 `placed_at` 起加總同一批 fills → **同一筆錢被算兩次**。
   （這正是 v130 在模擬盤實證過的 +1.30 R 虛增，同一個機制。）
3. **日虧熔斷失準**：`day_pnl` 被灌大一倍。若那天是賺的 → 帳面盈餘虛胖 →
   **該熔斷時沒熔斷**（危險方向）；若是虧的 → 提早熔斷（保守方向，可接受）。

第 3 點與 r38 已記錄的另一個瑕疵（`manage_positions:512` 用對帳當下 UTC 日、
而非成交當下記 `day_pnl`）**同檔、同函式、同一個熔斷口徑**——兩個都是在污染同一本帳。

### 修 A：下單前加同幣同向在場閘

位置：`consume_intents_live.py` 下單迴圈，擺在日虧熔斷檢查（733-734）之後、
張數換算（735）之前。

```python
if any(r["inst_id"] == intent["inst_id"] and r["pos_side"] == intent["pos_side"]
       for r in _load_positions().get("open", {}).values()):
    print(f"⏸ {iid} {intent.get('symbol')} 同幣同向已在場——本輪不接"
          "（OKX hedge 併倉會使已實現損益無法歸屬兩單）")

```

`continue` 而不記 `done`，沿用 733-734 熔斷日的既有慣例：不是永久拒絕，
是這一輪不接；倉平掉後若 intent 還沒過期就自然接上。

副作用（可接受，且方向正確）：401 斷流期對帳會早退，`ps["open"]` 可能留下已在交易所
平掉、但本地還沒銷帳的殘影 → 這道閘會擋掉新單。**這是 fail-closed，與斷流期本來就
零送出的現況一致**，不新增風險。

### 修 B：熔斷記帳改吃成交當下的日（r38 已提，規格在此補完）

`_realized_pnl_since()` 迴圈裡已經在讀 `f["ts"]`，順手回傳最後一筆 fill 的 ts；
呼叫端 512 行改 `dk = _day_key(last_ts)`，取不到就退回 `_day_key()` 保持記帳（fail-safe）。

**r38 沒講到、但一定要一起處理的一點**：532-533 行會把 `day_pnl` 修剪成只留 14 天。
回填舊日期時若那個 key 比 14 天前還舊，會在同一次呼叫裡**被立刻剪掉、損益無聲蒸發**。
規格：寫入前把日期夾到保留窗內——
`dk = max(_day_key(last_ts), _day_key(time.time() - 14 * 86400))`。
本次斷流只有 ~26.5h，踩不到，但這是修 B 自己引進的新洞，別留。

## 為什麼順序是「趁 401 還壞著的時候修」

401 斷流至今 202 輪零送出，這段期間**動真錢執行器的碼是零風險的**——沒有在場倉位
（`open` 為空）、沒有正在飛的單。等使用者把 IP 補上，執行器第一件事就是把 outbox 裡
12 張 ALIVE intent 依序送出去；那之後只要有任何一個倉活過 6 小時，修 A 擋的那個情境
就從紙上變成線上。

**斷流不只是損失，它同時是一段免費的維護窗。** 建議把這兩個修塞進這段窗裡，
而不是等 401 好了、真錢重新開始流動之後再排。
