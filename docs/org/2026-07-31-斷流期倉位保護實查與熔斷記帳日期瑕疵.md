## 二、查到的事實（依碼）

### 事實 1：止損是「交易所側」的，斷流時仍然有效 ✅

每一筆進場單都是**市價單直接附掛 OCO**送出去的，止損價寫在下單參數裡（`tools/atk_consumer/consume_intents.py:570-581` 的 `_leg_args`）：

```
--ordType market  --sz <該腿張數>
--tpTriggerPx <該腿的 TP>  --tpOrdPx=-1
--slTriggerPx <整段止損>   --slOrdPx=-1
```

也就是說，止損**不是**由我們這邊每輪去輪詢價格、再決定要不要送平倉單；它一送出就存在 OKX 的伺服器上，由交易所自己觸發。

**推論**：我們這端被 401 全鎖死的期間，交易所並不知道也不在乎——在場倉位的止損／止盈**照常會被觸發**。
所以「斷流時在場倉位＝裸倉」**不成立**。上一輪那句「401 會同時鎖死進出場」，對「保護性出場」（止損、止盈）是錯的。

這也順帶說明 v140 三腿分批止盈的設計是穩的：三腿各自帶自己的 TP、共用同一個止損價，TP1 觸發只平那一腿、其餘腿的止損續存——這個階梯完全在交易所側維持，不依賴我們的行程活著。

### 事實 2：真正在斷流期失效的，是這三件（且只有這三件）⚠️

讀 `manage_positions`（`consume_intents.py:492-534`）與主迴圈：

| 失效項 | 機制 | 斷流期後果 |
|---|---|---|
| **① 逾時強平** | 持倉滿 `TIMEOUT_HOURS = 24.0` 小時→本地判定→送 `swap close` | 這個平倉指令**會被 401 擋**。倉位不會在 24h 被砍掉，會一路續抱到 TP 或 SL 被交易所觸發為止（或人工處理）。這是真正失去的保護，但它是「時間紀律」不是「風險上限」——風險上限仍由交易所側 SL 守住。 |
| **② 對帳／損益回讀** | 每輪查 `account positions` 比對，查不到就早退不動（`:498-500`） | 401 → 每輪早退，已了結的倉不會被記帳，`day_pnl` 停止更新。這是 fail-closed 的正確設計（寧可不動也不誤判平倉），但帳會停在斷流前那一刻。 |
| **③ 新進場** | 已知 | 全擋，零損失（本次已實測 172 輪皆未送出）。 |

另外確認：**沒有**任何本地的保本／移動止損管理邏輯會在斷流時失效——因為根本沒有這種邏輯（與 `stop-management-ab-verdict` 定案一致：A_fixed 固定止損為預設，刻意不設保本）。這點反而讓斷流的暴露面比一般交易系統小。

### 事實 3（新發現）：熔斷記帳把損益記到「對帳當下那一天」，不是「平倉那一天」🐛

`manage_positions` 認定一筆倉已了結時，這樣記帳（`consume_intents.py:512-513`）：

```python
dk = _day_key()                       # ← 對帳當下的 UTC 日期
ps["day_pnl"][dk] = ... + pnl
```

`_day_key()` 不帶參數＝取**現在**時間（`:448-449`）。但這筆損益真正發生的時間是「交易所觸發 TP/SL 的那一刻」，可能是好幾小時前。

- **平時**影響極小：每分鐘跑一輪，對帳延遲約 1 分鐘，只有剛好跨 UTC 午夜的那一分鐘會記錯日。
- **斷流時被放大**：這次斷流 26.5 小時。如果期間有倉被 SL 觸發，那筆虧損會等到 401 修好後才被記帳，並被記在**修好那一天**。後果是：真正虧損那一天的**日熔斷不會觸發**（帳上是 0），而修好那天憑空多一筆虧損、可能誤觸當日熔斷。
- **週熔斷不受影響**（近 7 日合計，日期挪動不改變總和）。
- 本次**沒有實際踩到**——斷流期間 `atk_positions_live.json` 的 `open` 是空的，無倉可記錯。

這是一個**潛伏瑕疵，被斷流放大**，不是斷流才有的問題。
