# 真錢消費器停擺時，帳本會自己安靜下來——不是痊癒，是沒人在跑

**輪次**：r74 · v176　**日期**：2026-08-01（台北）　**CEO 狀態**：BLOCKED_ON_USER

---

## 一句話

真錢執行器的健康檔一旦超過 15 分鐘沒更新，帳本上唯一那條真錢阻塞就會**自己消失**，
渲染出來跟「一切正常」一模一樣。今天 01:13 起這件事正在發生：機器改吃電池，
`ATKLiveConsumer` 排程設了「電池模式不啟動」，於是消費器每分鐘的班全部被略過。

---

## 怎麼被發現的

r73 的工作收尾、跑例行盤點時，發現 `atk_consumer_live_health.json` 的
`consecutive_fail_rounds` 卡在 **1260 不再增加**。此前它每分鐘 +1（r72 量到 1227、
r73 開場量到 1260，中間對得起來）。

逐項量測，不靠推測：

| 量測點 | 值 |
|---|---|
| `ATKLiveConsumer` LastRunTime | 凍結在 **01:13:01** |
| NextRunTime | 每分鐘往前跳（01:29 → 01:30 → …）＝觸發器正常 |
| NumberOfMissedRuns | **持續累加**（15 → 16 → …）＝每次觸發都被略過 |
| 是否有卡住的舊實例 | 無（找不到任何 `run_live_once.ps1` 行程） |
| 排程設定 | `DisallowStartIfOnBatteries = True`、`StopIfGoingOnBatteries = True` |
| `GetSystemPowerStatus` | **未接外部電源**、電池 76% 放電中 |

根因確立：**機器改吃電池 ⇒ 該排程整個不跑**。這不是 bug，是排程本來就這樣設的；
會出事的是**它停了而沒有人會知道**。

---

## 真正的缺口：停擺被渲染成「沒事」

`live_exec_verdict()` 有一道 900 秒新鮮度閘，健康檔太舊就回 `None`。

那個**理由**是對的——不可拿昨天的 streak 當今天的阻塞（舊快照陷阱）。
錯的是**輸出**：它把「執行器整個停擺」和「一切正常」渲染成同一個空白。

實測當下健康檔已 1074 秒沒更新；再過一次帳本寫入就會跨過 900 秒，
`blockers` 裡那條 401 會安靜地不見。任何人（包括下一輪的監督員——**每一輪都是全新
session、只能從帳本讀狀態**）看到「沒有真錢阻塞」，最自然的讀法就是**痊癒了**。

這正是 **r33 假痊癒**的形狀換一個入口：那次是空轉輪騙過了「有無故障訊息」，
這次是停擺騙過「有無阻塞紀錄」。也是「未知 vs 確認沒有」在真錢路徑上的**第七處**
（前六處：孤兒閘／部位帳／健康檔讀／已處理清單／健康檔寫／熔斷損益漏記）。

停擺期間的實質代價與斷流期完全一樣：訊號送不出去，而且 trade-intent 一到
`expires_at` 就**永久丟棄、修好也不補送**。

## 修法（v176）

新增兩個純函式，`live_exec_verdict` 一行都沒動：

- **`ac_power_online()`** — Windows `GetSystemPowerStatus`，回 True／False／**None＝未知**。
  ⛔ 量不到不可折成「有接電」，那就是拿代理值當事實。
- **`live_stall_verdict()`** — 健康檔太舊（或沒有可信時間戳）就回報「消費器沒在跑」。

歸屬照 `live_exec` 的既有規矩分流：

- 量到**沒接外部電源** ⇒ `user_actionable=True` ⇒ 進 `blockers`（接上電源就會自行恢復，球在使用者）
- 有接電，或電源狀態量不到 ⇒ 進 `system_faults` ⇒ state 壓成 STALLED（原因不明，該查排程與腳本）

### ⛔ 刻意不做的事

- **健康檔不存在不報停擺**。那是「未知」（可能根本還沒部署過執行器），憑空報會變成慢性假警報。
- **兩道閘共用同一個門檻**（900 秒）。差一秒都不可以兩邊都不報——有專門的邊界測試釘住這條縫。
- **沒有動排程設定**。把 `DisallowStartIfOnBatteries` 關掉＝讓真錢執行器在沒插電時也跑，
  那是使用者的決定不是我的；而且 `StopIfGoingOnBatteries=True` 會在拔電當下**砍掉執行中的
  實例**，如果剛好砍在多腿下單的中間，就是 r46 那個孤兒部位的洞。已列 WAITING_ON_USER ⑨。
