# v196：設定覆寫檔「壞掉／讀不到」不再折成「從來沒設過」（同物種第 16 次）

日期：2026-08-01（監督員 Layer 2 第 90 輪）
檔案：`botconfig.py`
測試：`tests/test_botconfig_overrides_unreadable.py`（10 條）

---

## 一句話

`bot_settings.json` 是**風險參數的唯一來源**，而舊碼把「這個檔壞掉讀不出來」
當成「使用者從來沒設過」——1R 會靜默換模式、總風險上限會靜默改變，
而且**下一次寫入會把其餘設定永久刪掉**。

---

## 為什麼這一處比前 15 次都更該補

前面 15 次補的多半是「監控／進度／健康」類的檔——挖空的是**看得見的東西**。
這一次挖空的是**跑起來會用到的風險參數本身**。

實測（本輪量的，不是推論）：

| 事實 | 量法 | 結果 |
|---|---|---|
| `bot_settings.json` 內容 | 直接讀 | 只有 3 把鍵：`RISK_PER_TRADE_PCT`、`TOTAL_RISK_CAP_PCT`、`SIGNAL_MODE` |
| `.env` 有沒有這幾把 | 只檢查鍵存在性（⛔ 不讀值） | `RISK_PER_TRADE_PCT` ❌ 沒有、`TOTAL_RISK_CAP_PCT` ❌ 沒有、`RISK_PER_TRADE_USD` ✅ 有 |

也就是說：**前兩把只有覆寫檔這一個來源**。檔一壞，它們就等於沒設過。

## 壞掉時實際會發生什麼

```
_load_overrides()  壞檔 → _OVERRIDES = {}   （靜默，零警告）
        ↓
pct = _f("RISK_PER_TRADE_PCT", 0.0, 0.0, 5.0)   → 0.0
        ↓
if pct > 0:                    ← 不成立了
elif _is_set("RISK_PER_TRADE_USD"):   ← .env 有 ⇒ **成立**
        ↓
1R 從「帳戶百分比」模式靜默切成 .env 裡的固定 USD 金額
```

同時 `TOTAL_RISK_CAP_PCT` 落回 tier 預設＝**總風險上限靜默改變**。
畫面上與「使用者從來沒設過百分比」**一模一樣**——這就是本物種的定義。

### 更糟的第二段：暫時讀不到 → 永久滅失

`set_override` 的形狀是「讀出整包 → 改一把 → 整包覆寫」。
所以在壞檔狀態下**任何一次**設定寫入（Telegram /settings 或優化器都會寫），
會把只剩一把鍵的 `_OVERRIDES` 整個寫回檔案 ⇒ 其餘覆寫**永久消失**。
而稽核軌跡還會記成 `before: null`——等於白紙黑字謊稱「這把鍵本來就沒設過」。

**暫時讀不到還有救，覆蓋下去就沒救了。**

## 根因（與 v157／v162-v166／v195 同一支）

`set_override` / `revert_key` 用 `write_text` 直接覆蓋＝**非原子**。
斷電（這台機器本來就會拔電跑）或被 watchdog／memguard 殺在寫到一半，
留下的就是讀不出來的半截檔 ⇒ **本模組有能力親手做出那個壞檔，再自己誤讀**。

## 改了什麼

- `_load_overrides()` 三態分明：
  - `missing`＝檔不存在，**合法的第一次**（新機器／剛清資料目錄）→ 保持安靜
  - `no_settings_file`＝連 data_dir 都取不到（自測路徑）→ 無檔可毀
  - 例外類別名／`NotADict`＝**故障**（檔在卻讀不出來）
- 新增公開 getter：`overrides_load_error()`（原始狀態碼）、`overrides_unreadable()`（只回故障）
- 故障留痕：進 `_WARNINGS` 並印出；同一個故障每行程只吵一次（避免洗版）
- **寫入端 fail-closed**：`_guard_overrides_writable()`——讀不出來就拒寫並拋 `RuntimeError`，
  同時把拒寫寫進稽核軌跡（`source="blocked:<err>"`、`before="<unreadable>"`）
- 寫入改**原子**（tmp + `os.replace`），失敗一律拋、⛔ 不再 `except: pass`；
  失敗時記憶體側回捲，不讓呼叫端以為成功
- `revert_key` 同樣走 guard 與原子寫

### ⚠️ 方向選擇：讀取端**故意不** fail-closed

在 `_load_overrides()` 拋例外會讓每一個 `import botconfig` 的行程當場死掉——
包含 watchdog 自己。代價遠大於病。所以：**讀取端照舊讓行程活著、但把故障說出來；
fail-closed 放在寫入端**，因為寫入才是把損害從「暫時」變成「永久」的那一步。

### 政策界線（⛔ 不要誤讀成寫入鎖回來了）

使用者 2026-06-20 拍板**移除** step0 寫入鎖，該決定不變：auto 仍可直接寫任何活鍵。
這次擋的**只有**「在讀不到既有覆寫的狀態下整包覆寫」這一種會造成永久滅失的寫法。
Telegram `/settings` 端本來就有 try/except，使用者會看到「設定失敗：RuntimeError」，
而不是以為改好了——這是本修補的預期使用者體驗。
