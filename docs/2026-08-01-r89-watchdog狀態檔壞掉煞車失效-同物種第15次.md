## 二、本輪治本的洞（第 2、3 項）

### 症狀（尚未在線上發生）
`watchdog_state.json` 若「存在但讀不出來」，舊碼：

```python
def read_json(p):
    try:
        return json.loads(p.read_text(...)) if p.exists() else {}
    except Exception:
        return {}          # ← 半截檔 / 權限 / 編碼 / 被寫成 list，全折成這個
```

於是 `main()` 讀到的是：

```python
last_restart = state.get("last_restart_ts", 0)  → 0    ⇒ GRACE_SEC 暖機窗直接跳過
restarts     = state.get("restart_times", [])   → []   ⇒ MAX_RESTARTS_HOUR 煞車失效
```

**兩道煞車同時解除**，而且畫面上與「乾淨的第一次啟動」一模一樣。其中
`MAX_RESTARTS_HOUR`（1 小時 5 次就停手 + 告警交人工）是本專案對「一啟動就崩」
的唯一防線——它失效的結果是：每 3 分鐘一輪、每輪都重啟 daemon、而那則
「watchdog 放棄自動重啟」的告警**永遠不會發出**。

`memory_guard()` 的兩處 `read_json(STATE)` 同理：冷卻戳記與告警節流戳記一起歸零
⇒ 沒有冷卻保證地每 3 分鐘殺一輪行程 + 洗版告警。

### 根因（與 v157／v162-v166 同一支）
`write_state()` 用 `STATE.write_text()` 直接覆蓋＝**非原子**。斷電或行程被殺在
寫到一半，留下的就是 `read_state()` 讀不出來的半截檔。也就是說 **watchdog 有能力
親手做出那個壞檔，再自己誤讀成「第一次啟動」**——自製壞檔再自誤讀。
本機斷電是有前例的（r76 電力哨兵那條線就是為此補的），這不是假想觸發路徑。

### 治法
- `read_state() -> (state, err)`：`missing`（合法第一次，保持安靜）／例外類別名／
  `NotADict` 三態分明。⛔ 反向護欄：檔不存在必須維持安靜，否則每台新機第一次跑
  都收到假告警。
- `write_state()` 改**原子寫**（tmp + `os.replace`）並**回報成敗**——回傳值是給
  呼叫端 fail-closed 用的：寫不回去＝重啟次數永遠累計不起來。
- `recover_corrupt_state()`：隔離壞檔（`watchdog_state.corrupt-<ts>.json`，留供事後
  查證）→ 發 Telegram → 重建。⛔ 不可安靜重建：把「煞車曾經失效」藏起來正是本物種
  每次的真正傷害。⛔ 也不可憑空填一個重啟次數（那是捏造）——告警的誠實說法是
  「這一小時的重啟史已遺失，預算從現在重新起算」。
- 修不好（連重建都寫不進去）→ **fail-closed：本輪起停止自動重啟，回 exit 3**。
  寧可這輪不自癒（人工還救得回來），也不要開一場無聲的重啟風暴。
- `memory_guard()` 兩處：狀態檔讀不出來就**跳過本輪**。純衛生的動作，跳過一輪
  毫無代價；在沒有冷卻保證下清理行程則是每 3 分鐘殺一輪。
- `read_json()`（只剩 liveness 用）行為不變（壞檔→視為心跳很舊＝偏向重啟，方向保守），
  但**補上留痕**：否則 liveness 永久壞掉時 watchdog 會每輪重啟卻沒人知道為什麼。
