# 401 白名單修好之後：第一筆真錢單的驗收清單

> 監督員 r65（2026-07-31 21:0x）產出。純文件，未動任何常駐模組。
> ⛔ 本檔不含出口 IP、不含 API key-id（那兩項只存在資料目錄）。
> ⛔ 401 未解前，v154–v167 一律不得宣稱「已在真錢實證」。

## 這份清單為什麼存在

先前每一輪的 next_step 都寫「401 修好後，優先驗第一筆新 intent 是否真的送出」。
本輪量到一件先前沒寫過、而且會改變那一刻該怎麼驗的事實：

**斷流期間，真錢執行路徑一共上線了 12 個版本，而這 12 個版本沒有任何一個
被成功的交易所呼叫執行過。**

也就是說，「401 修好後的第一筆單」不只是一次恢復驗證，
它同時是 v143→v166 這 12 版程式碼在真錢路徑上的**第一次實跑**。
兩件事撞在同一筆單上，驗收就不能只看「有沒有送出去」。

## 量測一：目前看得到的故障，全部同源

執行器健康檔的 `class_counts` 是**以「輪」為單位**累計的
（同一輪同一類只記一次，見 `update_health`）：

| 類別 | 輪數 |
|---|---|
| `auth_ip_whitelist`（401 白名單） | 1302 |
| `query_fail`（查單失敗 → fail-closed 不下單） | 770 |
| `leverage_fail`（設槓桿失敗） | 92 |
| 總輪數 `rounds_seen` | 1311 |

由 1311 − 1302 = 9 可得：**沒有 401 的輪最多只有 9 輪**。
因此 770 輪 `query_fail` 裡至少 761 輪、92 輪 `leverage_fail` 裡至少 83 輪，
**確定與 401 同輪發生**。配合程式面（`ensure_leverage` 與查單都是直接吃 OKX
CLI 的 401 輸出而失敗），結論是：

> 目前健康檔上看得到的三類故障是**同一個根因的上下游**，
> 不是三個要分開修的問題。補好白名單這一件事，預期會一次讓三類都消失。

⚠️ 這個結論的**邊界要講清楚**：它只證明「目前會發出訊號的故障沒有第二個獨立根因」。
它**不能**證明認證通了之後一切正常——因為認證後的程式碼路徑
在整段斷流期一次都沒跑過，有問題也不會發出任何訊號。這正是量測二。

## 量測二：哪些程式碼「跑過」、哪些「一次都沒跑過」

斷流期上線、且改到真錢執行器的 12 個 commit（v143、v151、v154、v155、v158、
v159、v160、v162、v163、v164、v165、v166）依「認證失敗時會不會被執行」分兩堆：

### A. 斷流期已被實跑過（只跑到失敗那一側）

這些每輪都在跑，線上已有行為證據，但**只證明了失敗分支**：

- 故障分類／嚴重度排序（`classify_failure`、`worst_class`）
- 空轉輪三態、假痊癒防線（v151 `update_health`／`finish_round`）
- 健康檔讀失敗、寫失敗的處理（v164／v166 `_load_health`／`_save_health`）
- 連續失敗告警與 Telegram 送出（v143，斷流期實際送出過）
- 部位帳、已處理清單「讀失敗＝未知」的分支（v163／v165）
- 孤兒偵測的「查詢失敗 → 判未知 → 擋新單」分支（v159）

### B. 一次都沒跑過（要靠第一筆成功的單才第一次被執行）

**這一堆才是第一筆單真正的風險所在**：

| 版本 | 未被實跑的東西 | 第一筆單要看什麼 |
|---|---|---|
| v154 修A | 同幣同向在場閘（防 hedge 併倉雙重記帳） | 有在場部位時，同幣同向新單確實被擋 |
| v154 修B | 熔斷記帳改吃「成交日」、夾進 14 天保留窗 | 了結後日/週熔斷數字有進帳且日期歸屬正確 |
| v155 | 設槓桿失敗 → fail-closed；算出的槓桿低於上限才擋 | 槓桿在交易所側**實際讀回**等於預期值（v99 教訓：不可只信帳本）——**v171 起這項已自動記錄，見下方註** |
| v158 | `timed_out()` 逾時平倉判定 | 首筆若走到逾時，確認真的平掉而非卡住 |
| v159 | `orphan_positions()` 的**成功**分支（查得到部位時的反向對帳） | 查詢成功時不誤判在場部位為孤兒（誤判會擋掉所有後續同幣同向新單） |
| v160 | `place()`／`ensure_leverage` 成功路徑的日誌輸出 | 日誌無明文 key-id（遮蔽在成功路徑上也生效） |
| v162 | 孤兒閘「未知就不接新單」在**查得到**時要放行 | 不會因為閘太保守而永遠不下單 |
| v163 | `_save_positions()` 寫入真實在場部位 | 部位帳落檔內容與交易所一致 |
| v165 | 已處理清單寫入（冪等去重） | 同一 clOrdId 不會被重下 |
| 全體 | 多腿進場 + `--slTriggerPx` 交易所端止損附掛 | **每一腿**都帶止損掛上去（r46 的核心保護） |

### 註：B 表第一項自 v171（r69）起可自動舉證

寫這份清單時，「交易所側讀回的槓桿值」這個數字**在任何檔案、任何 log 行裡都不存在**：
`ensure_leverage()` 只看設定呼叫的 exit code 就回 True，從來沒有讀回過交易所的實際值。
也就是說，第一筆單當下若沒有人剛好在線上手動去 OKX 查，倉一平掉證據就永遠沒了。

v171 把它變成自動產出（零額外呼叫——`account positions` 的回應本來就帶 `lever`，之前整個丟掉）：

- **下單時**：部位帳那筆記下 `lev`＝當時算出的槓桿（比較基準）。
- **每輪對帳時**：讀回交易所側 `lever`，寫進 `lev_exchange` / `lev_verdict` / `lev_checked_ts`。
- **判定三態**：`match` / `mismatch` / `unknown`。⛔ 未知永遠不算相符——v171 之前開的倉
  沒有 `lev`、交易所也可能不回 `lever`，這兩種一律 `unknown`。
- **證據落點**：第一次讀回（或判定改變）時在 `atk_live.log` 印一行「交易所側槓桿讀回」。
  **倉平掉後部位帳那筆會消失，log 行才是留得住的證據** ⇒ 驗收時去 grep 這一行。
- **對不上時**：記 `lev_mismatch` 進健康帳，由既有的連續輪告警機制接手。
  ⛔ 不自動調槓桿、不自動平倉、不擋新單（比照 `orphan_position` 的處置）——
  斷流期已累積十幾版沒在真錢路徑跑過的碼，此刻不該再加一道沒跑過的閘去擋第一筆單。

⚠️ v171 本身同樣**沒有在真錢路徑跑過**（斷流期 `account positions` 一定失敗、根本走不到讀回），
所以它是加進 B 表、不是從 B 表劃掉一項。

## 建議的驗收順序（401 修好之後）

1. **先確認是「真的通了」不是「沒東西可送」**（r33 假痊癒教訓）：
   看 `atk_consumer_live_health.json` 的 `last_ok_ts` 有沒有**前進**、
   `consecutive_fail_rounds` 有沒有歸零，且該輪要有實際成功呼叫（`_ROUND_OKS`）。
   待送匣目前是抽乾的，補好白名單後會有一段「零故障訊息」純粹因為沒東西可送——
   ⛔ 那段期間不可宣告痊癒。
2. **第一筆新 intent 送出後，逐項對照上面 B 表**，尤其三項不可跳過：
   交易所側**讀回**的槓桿值、**每一腿**的交易所端止損、部位帳落檔與交易所一致。
3. 三項都對，才可以說 v154–v166 在真錢路徑上「開始有實證」；
   在那之前，這 12 版一律只算「單元測試與模擬盤層級已驗」。

## 一句話

白名單只有一個洞要補，補完預期三類故障一起消失；
但補完的那一刻，是 12 版沒跑過的程式碼第一次碰真錢——
所以第一筆單要當成「上線首航」驗，不是當成「恢復確認」驗。
