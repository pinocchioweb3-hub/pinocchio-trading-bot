# v188 / r81：watchdog「列不出殭屍清單」不再假裝成「一個都沒有」

日期：2026-08-01（監督員第 81 輪）
狀態：已落地、已提交、**已在真實環境雙向實證**（不涉真錢、不涉對外發布）
CEO 狀態：BLOCKED_ON_USER（孤兒部位 WLFI + demo_guard 皆為使用者決策）→ 本輪只做平行安全工作

---

## 1. 這次修的到底是什麼

`watchdog.py` 的 `_stale_claude_runners()` 負責回答一個問題：
**「現在機器上有幾個符合可殺指紋的 Claude 排程殭屍行程？」**

它原本長這樣（節錄）：

```python
r = subprocess.run([...], capture_output=True, text=True, timeout=60)   # text=True＝跟隨 locale
if r.returncode != 0 or not r.stdout.strip():
    return []
...
except Exception:
    return []          # ⛔ 這一行是問題本體
```

於是**任何**量測失敗——PowerShell 非零退出、逾時、輸出不是 JSON、解碼失敗——
都會回一個空表，而空表的意思是「機器上一個殭屍都沒有」。

r80（上一輪）自己踩到了它：監督員標準指示要求執行 Python 時加 `-X utf8`，
一加上去，Python 就用 UTF-8 去解 PowerShell 的 cp950 中文輸出 →
`UnicodeDecodeError` → 被 `except` 吞掉 → **印出「0 個殭屍」，exit code 還是 0**。
當時線上實際有 **4 個**（`Get-CimInstance` 交叉驗證）。

這是本專案同物種第 8 次：**「量不到（未知）」被折成「沒有」**。
前 7 次分別發生在 IP 哨兵、電力哨兵、部位帳、健康檔讀寫、已處理清單、
損益查不到就 pop 掉紀錄……這一次特別值得記，因為中招的是**偵測器自己**。

### 在 memguard 這條路徑上，後果是什麼

- 常態清掃段（commit < 88%）：量不到 → `stale=[]` → `len(stale) < 4` → **靜默 return**。
  沒有 log、沒有告警、exit code 0。「常態清掃永遠不觸發」而且沒有任何人看得見。
- 緊急線段（commit ≥ 88%）：量不到 → 印出「無符合指紋的殭屍可清（App 端請人工處理）」。
  這句話**是錯的**——它宣稱「量到 0 個」，實際是「沒量到」。人照著它去重啟 App，
  卻不知道 watchdog 其實已經瞎了。

---

## 2. 改法（v188）

1. 新增 `_RunnerProbeError`。量不到就**拋例外**，⛔ 不回空表。
   回 `[]` 從此只代表一件事：真的一個符合指紋的都沒有（退出碼 0 + 輸出為空）。
2. 新增 `_decode_console()`：改用 bytes 收 stdout，依序試 locale → cp950 → utf-8，
   全失敗才 `ascii + errors="replace"`（保住 JSON 的 ASCII 骨架）。
   ⛔ 這一層永不拋例外，也永不用空字串假裝成功。
3. 新增 `_probe_runners_or_log()`：量不到 → 回 `None` + 寫本機 log
   「殭屍 runner 清單量測失敗（原因）——⛔ 未知不折成 0 個，本輪不動作」。
   兩個呼叫點都改走它。
4. 未知時的處置：**不動作**（未知狀態下殺行程與不殺，只有不殺是安全的），
   且**不寫 `memguard_last_ts`** —— 一次解碼失敗不該吃掉接下來 10 分鐘的清理機會，
   3 分鐘後的下一輪就能重試。
5. 緊急線上又量不到＝最需要出聲的組合：本機留痕之外，另推一則**措辭不同**的
   Telegram 告警（「列不出殭屍清單（量測失敗）」而非「無殭屍可清」）。
   走既有 `_memguard_notify` 節流，不會洗版。

⛔ **完全沒有動的東西**：`MEM_MIN_AGE_MIN`(90 分)、常態清掃的「4 個」門檻、
`MEM_COOLDOWN_SEC`(600s)、`MEM_EMERGENCY_PCT`(88%)、可殺路徑指紋。
那幾項是使用者裁量中的待決項（WAITING_ON_USER ⑤），本輪只治「量測誠實度」。

## 3. 驗證

**新測試先在舊碼上失敗**（非虛設檢定）：`tests/test_watchdog_runner_probe_honesty.py`
10 支，在改動前的碼上 **9 紅 1 綠**（唯一那支綠是控制組「真的 0 個仍要是 0 個」）。
改動後 10 綠；併既有 `test_watchdog_memguard_alert_throttle.py` 7 支，共 **17 綠**。
`py_compile` 通過。

**線上雙向實證**（同一時刻、同一台機器）：

| 量測環境 | 結果 |
|---|---|
| A. 排程實際環境（無 `-X utf8`） | 5 個 runner，其中 3 個 ≥90 分鐘 |
| B. 陷阱環境（`-X utf8` + `PYTHONIOENCODING=utf-8`） | 5 個 runner，其中 3 個 ≥90 分鐘 |
| C. 獨立交叉驗證（直接 `Get-CimInstance`） | 5 個，年齡 233/186/126/66/6 分 ⇒ ≥90 分者 3 個 |

B 欄在改動前會回報 **0 個**。A/B/C 三者一致＝陷阱已封。

**RB-1 不適用**：`watchdog.py` 是 Windows 排程每 3 分鐘起一個新行程的獨立腳本，
不是 daemon 常駐模組，存檔即生效、不需停 daemon、不需重啟。本輪未動 daemon、
未重啟、未下任何單。

## 4. ⛔ 不可過度宣稱

- 常態清掃至今**仍是零次線上觸發**：本輪量到符合指紋 5 個、但 ≥90 分鐘者只有 3 個
  （門檻要 4 個），commit 54.2%（遠低於 88% 緊急線）。
  ⇒ **不得宣稱「效能日衰已修」**。要等 `watchdog.log` 出現第一行「常態清掃」才有實證。
- 本次修的是「量測失敗不再變成假的 0」，**不是**「殭屍清得更乾淨」。
  它的價值在於：下次真的量不到時，會有人看見。
- 這個洞在生產環境（cp950 locale）**尚未實際發生過**——它只在 UTF-8 模式下必然發生。
  ⇒ 屬預防性治本，非事故修復。
